# Changelog

Each version of Hoprig, newest first. Hoprig installs from the main branch of its repository; `hop update` brings the newest version, and **Settings → Version and updates** shows it in the dashboard.

## 0.4.0 (27 November 2026)

This version is about starting, and about fewer things on the screen. One line installs Hoprig on Windows, macOS or Linux, asks nothing, and ends with your browser open and signed in. The menu has six items, Home says what needs you, and a conversation is one session whether you use it in the App (the dashboard's chat view of a session) or in a terminal. The gateway that comes with Hoprig (a program that passes a coding tool's requests on to a provider) is set up with one press. Windows is new: the installer and the whole test suite run on GitHub's Windows, macOS and Linux machines, but a real home Windows PC has seen less of Hoprig than Linux has.

### What changes when you update

- **The menu has six items.** Home, Work, Projects, Providers, Computers and Settings; on a phone the bar has five tabs and Settings is the gear at the top. The Operator page and the More page are gone: an old link to either opens Home or Settings. What the Operator listed is now rows of **Needs you** on Home.
- **Some pages moved, and every old link still lands.** **Skills** and **Memory** are tabs of **Projects**; Memory is the page that was called AI brain, the folder with the rules, skills and memory your coding tools share. Tia is opened from her own button, and Work, Computers and Settings are shorter (told below). The light and dark choice is only in **Settings → Appearance**.
- **A conversation is one card on Home.** A conversation you open in the App and in a terminal is one card, not two or three. Home's groups are **Needs you**, Working and **Ready**.
- **The queue has no switch.** It always sends. An old switch that was off is still honoured, with **Turn it on** in the queue's banner.
- **The box is not offered on Windows.** Where Hoprig told you to use it inside WSL 2 (Windows' own Linux), it now says the box is not offered on Windows and that such work runs on a Linux or Mac computer of yours.
- **TRouteAI lives in Hoprig's own folder.** Install puts version 1.0.13 there, so a start from a session and one from a service use the same data. Adding an account from a list, opening TRouteAI signed in and its public address need that version: with an older copy the page says so, with **Update** beside it. A copy that npm already put on your computer stays in use until you press Install or Update; nothing changes by itself.

### Starting

- **One line installs it on Windows, macOS and Linux, and asks nothing.** It says what it installs, ticks each step and does it: Node.js (on Windows into your own folder, with no administrator window), Git where it is missing, Hoprig, Claude Code, and the dashboard, which starts with the computer. On Windows it stops, and says so, when the window runs as administrator.
- **Your browser opens signed in.** At the end Hoprig opens the dashboard on this computer, already signed in, so there is no password to find. The Start menu entry on Windows, or `hoprig link --open`, opens it again signed in.
- **The first page says the next step.** Home shows **Welcome to Hoprig** with two steps: **Sign in to Claude**, then **Start your first chat** with **New project** or **My own folder**. With no Claude plan, **No Claude plan? Pay as you use** signs in with a key instead.
- **Only this computer may open the dashboard at first.** The first run has no question about it; to use it from your phone, turn that on later in Settings.
- **A later `hoprig setup` is the full run.** It asks what a first run does not, for a second computer or for someone who wants to choose.
- **A fresh install is plainer.** The first provider is called **Claude account**, reopening sessions after a restart is on, and on Windows the Python and Terminal extras kits are one tick away instead of on by themselves.
- **Hoprig keeps itself running.** On Linux, macOS and Windows, a dashboard that dies is started again by the service after 3 seconds. One that keeps failing is handed to a keeper (on Linux after 5 failed starts in a minute, on macOS and Windows a check every minute), which writes the service files again and tries once more; it does nothing after you stop Hoprig yourself.
- **An update that does not start is put back.** When the new version does not answer within a minute, the version before it comes back and Home says so under **Needs you**. This holds for a Hoprig installed with npm; a copy from git is never swapped.

### The App chat

- **It looks like Claude Code's.** Your message is a plain grey bubble on the right; a long one is folded after 8 lines with **Show more**, and **Copy** and **Rewind to here** sit under it. Tool calls are one quiet line each, the to-do list and permission cards are neutral, and code sits on a grey well with a **Copy** button.
- **One line says what Claude is doing, where your eye is.** At the end of the conversation it says Thinking, Running with the command, Writing or Compacting, with the time, and a sent message takes the conversation to its end. The title bar and the session list say the same state words everywhere: Working, Working in the background, Needs your OK, Finished, Ready, Ended, and Limit reached.
- **A message you send while Claude works waits as a faded bubble.** It says it is read after the current step, with **Edit** and **Remove**; a long one stays inside the column.
- **Background tasks are one line above the box.** It says the task and how long it ran, or how many there are; a press opens each task with its **Stop** and its output.
- **On a phone the box is one rounded box.** The text field is 16 px, and under it one row: **+**, one pill that says the mode and model, the microphone and one round **Send** or **Stop**. The pill opens the sheet **This session** with the mode, model, effort and context; every press is 44 px.
- **A phone has the session list over the chat.** The **Sessions** button opens it from the left with **Home** at its top, and the title and its menu are one sheet. A reply has one **Copy** under its turn.
- **The list can be hidden, and a terminal opens under the chat.** The panel button at the left of the title bar (or `Ctrl+\`) hides the list; **Terminal** opens a shell in the session's folder.
- **Links, file names and git are in the chat.** A link opens in a new tab; a file name opens the editor at that line; **Create PR** asks Claude Code to commit, push and open a pull request, and the PR line shows its checks.
- **The session menu is shorter.** **Fork** makes a copy of the conversation, a click on the title renames it in place, and **Archive** asks nothing and has **Undo**.

### The shape of the product

- **Home says what needs you.** **Needs you** comes first, then Working and Ready; a group with nothing in it is not drawn. Each row says in plain words what is wrong and has one button, and the number on the Home icon is the only badge in the menu.
- **New session is one tap.** **New session** lists your projects, and a tap on one starts a chat there. Everything else (the coding tool, App or terminal, the mode, the model, a branch of its own, an earlier conversation) is behind **More options**.
- **Projects has one door in.** **Add project** offers the three ways: a new project, one from GitHub, or one found on this computer. Each project is one row with its state and **New session**; sync, other folders and groups are one fold at the end.
- **Work has four tabs.** **Tasks** (with what waits for your yes and what is due this week, and Go live as a fold), **Plans**, **Schedules** and **Activity** (with what is running now and what was done).
- **A computer has three tabs.** **Overview**, **Setup** (the checks, the ones to fix first) and **Advanced** (programs, ports, service and the rest). Its health is in Setup and Advanced.
- **Settings has seven rows.** New sessions (with Hands-off, Hoprig answering a coding tool's questions for you), Notifications, Appearance, Security and sign-in (with the public link), Tia, Automations and Version and updates. Every old settings address opens its new place.
- **Tia is one button, and her switches are in one place.** Her chat opens from the round button (the sparkle on a phone), and **Settings → Tia** opens with her on switch and her level, then closed folds.
- **Providers shows your accounts first.** The gateway is one row, and the rule for what happens at a usage limit is one row.
- **Smaller changes.** Page heads are one short line on a phone, and a press is at least 44 px on a touch screen.
- **A new session starts in the project, not in a code folder inside it.** New session, the Projects page and the first chat start in the project's own folder, one row per project; a code folder has no row of its own, and **Another folder…** reaches one.
- **Hoprig mends some things by itself, with no model.** A gateway or the public link that does not answer is restarted, a session whose tool died is reopened where it stopped with nothing sent to it, a test's left-over processes are ended, and its own old files are cleaned when the disk is over 90% full. Each leaves a line and costs no usage; **Settings → Automations → Mend problems by itself** turns it off, and everything else stays a row of **Needs you** with one button.
- **Tia can manage Hoprig itself, by one rule.** She does by herself only what changes nothing but Hoprig's own state and can be undone with one press, and only when **Tia acts by herself** is on, in Settings, Tia; a stop, money, another computer or anything hard to undo is a card you tap.
- **There is a list of what she never does, at any level.** Signing in or out, keys and passwords, the credentials folder, opening the computer to the internet, adding a computer, deleting work and raising her own rights stay yours, and a card is never confirmed by voice.
- **You can speak to Tia.** The microphone beside her box (and the App's message box) uses the browser's own speech recognition, so it needs a browser that has it, such as Chrome, Edge or Safari, and an https address or this computer itself. A message you speak is sent 1.5 seconds after you stop unless you touch the box, and her answer to it is read aloud by the browser (a typed message is never read aloud); **Settings → Appearance** has the switches for reading aloud.

### One conversation, one session

- **App and terminal are the same conversation.** **Continue in Terminal** in a chat's menu opens it in a terminal; **Open in App** on a terminal's page brings it back; the chat record is kept, so a conversation is never open nowhere.
- **Continue here no longer starts a second conversation.** On a terminal that was made outside Hoprig and adopted, a hand-over used to run the terminal's own first line again, which started a new conversation with the same first message. It now only takes the conversation over.
- **A hand-over ends the terminal Hoprig made.** A plain shell left behind is not listed on Home as a conversation of its own.

### The gateway, built in

- **One press sets it up.** On **Providers → Add provider → Other providers**, **Set up** installs TRouteAI when it is missing, starts it, makes a key and writes the provider. `hoprig addons setup trouteai` does the same with no questions, and every failure ends in one sentence with the next step.
- **It has a page of its own.** On **Providers** a press on the **TRouteAI** row opens a page with its state, **Open TRouteAI**, its accounts (test, turn off or on, remove, read the limits now), **Combos** and the keys Hoprig made. When a check finds a model name with no combo, **Make the combo** makes it.
- **Its start, update, log and removal are on Health.** **Health → Gateways** has Restart, Log, Update, Remove and Password; Remove takes only Hoprig's own copy away and keeps your data.
- **A public address, only by your press.** The **Public address** fold gives TRouteAI an address on the same link as Hoprig's, off until you turn it on, and refused while the gateway still has its first password.
- **Hoprig keeps no key of full power.** The key for your sessions comes from the gateway's own command, and Hoprig asks the gateway for anything else only from this computer and only a program of your own user.
- **A server set up with a root login works again.** Hoprig's move to its own user used to leave the gateway behind, and as that user its program was not found; both are mended.

### A mode beyond Bypass

- **Allow everything goes beyond Bypass permissions.** In Bypass permissions, in which Claude Code runs every command without asking you, Hoprig still holds a command it cannot read and a delete it cannot judge. In a session you put into **Allow everything** yourself nothing is held, and each thing leaves one quiet line. One thing still stops: a delete that Hoprig reads for certain as removing your whole home folder, workspace, projects folder or disk.
- **It is yours alone, and off until you allow it.** It is Claude Code only, off until **Allow bypass permissions mode** is on in **Settings → New sessions**, never as root, and the first time on a computer it asks once. Tia, a schedule, Work and another computer never start a session in it.

### Projects in step, credentials between your computers

- **What is not in step is said on Projects.** **Not in step** lists a project whose git server has more, or that was changed on both sides, one row and one button each; **Get it** brings what the server has. When everything is in step nothing is drawn.
- **Hoprig can bring a project up to date by itself, only where it is safe.** Every 30 minutes it looks, and a project that is only behind, with nothing changed and no session open there, is moved forward; never a merge, never a push. The switch **Move projects that are only behind in …** is on for your projects folder and off for groups of your own.
- **Credentials move between your own computers, sealed.** **Move to another computer**, next to where the credentials folder is kept, seals the files for the other computer, shows what would change by name and size, never a value, and writes only the new ones; a file that differs waits for **Replace**. **Trust** takes only a key that the other computer's own brain shows, never one offered over the link.
- **A computer you mark as not yours takes credentials one project at a time.** A rented server or a friend's never gets everything.

### Fewer tokens

- **A coding session through an API or a gateway keeps its start in the provider's cache.** The start of every request is now the same, so the provider reuses it; a subscription sign-in is untouched.
- **The rules file of a new install is a third the size.** About 300 tokens where it was about 800, in every request of every session; a file already installed is never changed.
- **A new chat starts with Ultracode off, and without its tool.** It no longer takes the setting of the folder's last chat, and a chat with it off is started without the Workflow tool, which saves about 6,000 tokens in every request. Hoprig adds none to a terminal session and asks no model by itself.

### Safety

- **Only your own page starts a session in the credentials folder.** The assistant and every other caller are refused, and **Files** refuses to copy or move a link into it.
- **What Tia reads of a session never shows a credential value.** The screen she reads of a session, also across a line break and an indent, has its credential values hidden.

### Windows and macOS

- **Windows: the install line, the first run and the tests.** The line was walked on GitHub's Windows machines four ways: a new PC with scripts off, scripts allowed, an administrator window, and Git missing. The log is plain text, your own Node.js stays first on the PATH, and the sign-in sheet says a tab Claude opened itself needs no code.
- **macOS: a chat on a branch of its own works in a Mac's temporary folder.** The folder is compared by its real place.
- **Not tried on a real home computer.** The Windows service, winget, a restart of the service and a console window opening during a go-live command were not run on a real Windows PC, and macOS was not run by hand with the installer.

### For contributors

- **The installer and the first run are checked on three systems.** `pack-smoke.yml` runs the install line on Windows, macOS and arm64 Linux, and the install walk in four Linux containers; the first-run walk is run on demand.
- **Every main page is measured.** A guard measures each main page at phone and desktop size against the rules of easy: for example at most six menu items, one badge, tabs under the head, no button repeated, and presses of 44 px.
- **Test files that passed only on their second run are named.** With `--again` a failing file runs once more by itself; one that then passes whole is named in a block that starts "⚠ PASSED ONLY ON ITS SECOND RUN:" and is a defect to look at.
- **Unused files are gone.** Three development scripts that nothing used and the logo sketches are removed.

## 0.3.6 (26 November 2026)

With this version Windows is experimental; before, it was not supported. Its tests pass on GitHub's Windows runners with Node.js 24 and 26, but about 835 of them are skipped there, each with its cause, and a skipped test proves nothing. Hoprig has run on one real Windows computer only, and what this version mends on Windows was not tried on it. Hands-off (Hoprig answering a coding tool's questions for you) and the box (a task's own copy of the project, with no network) do not exist on Windows. A few changes show on Linux and macOS too: they are under On every system.

### What changes when you update

- **Do not start a move to another user from an older Hoprig while this one moves.** The lock of a move of Hoprig to another user now holds the identity of the process that moves, and a Hoprig older than this version reads that lock as no lock, so it would not be kept out.

### Windows: what was not tried, and what works differently

- **Not tried on a real Windows desktop.** Task Scheduler (which starts the dashboard as a service), winget, icacls (the program that hands a folder back to you), a restart of the service and a coding tool's `.cmd` launcher in a real console have not run on a real Windows desktop. Nor was it seen whether a check or a go-live command (the commands that Go live, on the Work page, runs for a project) opens a console window while it runs: such a command now runs without a console of its own, so a console program it starts (npm, node, git, cmd) may open a window on the desktop for as long as it runs, and closing that window ends that program.
- **A go-live command ended at its time limit also ends a server it started in the background.** On Linux that server goes on running.

### Windows: set-up and the desktop

- **The desktop no longer waits for PowerShell.** On Windows the desktop's Task manager (with its disks, network and ports) and Services load at once, where they waited about 17 seconds for PowerShell to load its modules. Taking over a dashboard that is still running no longer waits that long before it can tell whether that dashboard is yours, and doctor and Health read who owns your folders without loading a PowerShell module.
- **Set-up and Health ask the system's own whoami.** A whoami that Git for Windows puts earlier on PATH (the folders Windows looks in for a program) can no longer make them misread whether set-up runs as administrator.
- **A program without a window is ended with Force.** Windows cannot ask a console program or a server to close, only end it at once: the desktop's Task manager says to use **Force** for such a program, and when you end one from the Operator it is ended at once, after the same checks.
- **Lines to paste are PowerShell lines.** Where Hoprig gives you a move or a removal of a workspace folder to paste, on Windows it is a PowerShell line (Move-Item, Remove-Item), a link is removed as a link without what it points to, and of two lines pasted together the second runs only when the first worked.
- Smaller things on Windows: a coding tool installed as a `.cmd` file is refused at its start, with the reason, when a word of its start holds a character that cmd.exe would read; text is typed for a coding tool only while its launcher still runs; a read-only workspace map file is named as what keeps the map from being saved; an error of a sync or a push no longer shows a folder's path with a drive letter or a network share; a check or a go-live run at low priority runs below normal priority.

### Windows: Files

- **Files packs names in any script.** On Windows, Files packs files and folders whose names have letters in any script (Hindi, Chinese, an emoji and others), which Windows' own tar could not pack.
- **Files unpacks them, and refuses an archive it cannot unpack there in plain words.** A .tar.gz, .tgz or .tar whose files have names in any script is unpacked. Such an archive is refused, with the reason, when a name in it could not be used on Windows: a character Windows does not allow, a part ending in a dot or a blank, a device name such as CON, or two names that differ only in letter case. An archive is refused as well when a name in it is one that Windows reads as git's own folder or as a private folder: with a dot or a blank at its end, with a part behind a colon, or the short name GIT~1. When Windows' own tar stops on a file name, Files says so and names the file.

### Windows: Go live and checks

- **A go-live command outlives a restart of the dashboard.** On Windows a go-live's update command and the servers it starts go on through a restart of the dashboard, keep their output up to its limit, and are ended as one tree.
- **A command at its time limit is ended with what it started, and only that.** On Windows a check or a go-live command that reaches its time limit is ended through its own process handle, so a program that Windows has just given its old process number is never ended in its place, nor five seconds later. A command left by a dashboard that stopped is ended only when Windows still shows it with the start it was recorded with; when it does not, nothing is ended and the answer says so. When the system cannot list its processes, such a command, and a command Tia runs, is still ended at its time limit, and the answer says that what it started may still run.
- **A step left by a dashboard that was ended is taken over.** On Windows a dashboard that comes back after a go-live restart, or its helper, now takes over a step left by the dashboard that was ended, even while the other dashboard or a reader still has the step's file open. The helper no longer gives up on a step after one look it could not decide.

### Windows: Tia's commands

- **A command Tia runs is ended at its time limit together with everything it started.** Her call no longer waits for a program that the command left running.

### Windows: the wall

- **The wall reads Windows' own spellings.** The wall is Hoprig's check that reads a command before it runs and holds the kinds that stay yours, such as a deploy or administrator rights. On Windows it now reads PowerShell's and cmd's spellings of Hoprig's folders and variables, a drive share as the drive it reaches, a short 8.3 name, and what cmd and PowerShell run behind their switches (also start, call, iex and a quoted program path), each in a bounded time. A place inside a command's text is compared as written, without asking the disk, and a line that names more than 64 places inside its texts is held.
- **Administrator rights are told by Windows' own programs.** gsudo, runas, Start-Process with RunAs and sudo.exe are read as administrator rights. An administrator command that names a Hoprig folder, a network share or a device path, or a short name or a drive-relative word that could reach a Hoprig folder, is refused, and so is a Windows shell started as administrator.

### Windows: locks and saving

- **A save no longer fails when another program has the file a moment.** On Windows, when two dashboards, or a dashboard and a `hoprig` command, saved the same file at the same moment, one of them could fail with a permission error (a page of the dashboard showed a server error). Such a save now waits a moment until the other lets go; the settings file and a run's record are read again once they are let go.
- **Sending into a session, Improve Tia and a move to another user try again.** On Windows, sending a message into a session, starting a round of **Improve Tia** and moving Hoprig to another user no longer fail with a permission error when Windows refuses a lock or state file for a moment: they try again and go on.
- **A lock left by a program that stopped is taken over.** Getting a project and the record of what Tia spent on paid use are each kept by a lock. On Windows such a lock left by a program that stopped is now taken over also while another program that wants it is reading it, so two gets of the same project at once no longer both end as busy, or go on without a lock, and the spending record is no longer answered as busy.
- **A hook or a command no longer fails when a lock's helper file stays a moment.** On Windows a hook (the small program of Hoprig that Claude Code calls at each step of a session) or a command no longer fails when the temporary file of a lock it took over could not be removed at that moment.

### Windows: runs by themselves and schedules

- **A scheduled run ends its whole tree.** On Windows a run that starts by itself at its time ends its coding tool and every process that tool started, one at a time and each checked by when it started, so a program that Windows has since given the same process number is never ended. The coding tool is started from its npm launcher. When a part could not be ended, the run says that its tool may still run, and keeps its own copy of the project until that program has closed.
- **A schedule whose run left its coding tool running is switched off.** On Windows, when a scheduled run's coding tool could not be ended, that schedule is now switched off so its next run does not start in the same project, and Work → Activity says to switch it on again in Work → Schedules once that program has ended. A schedule that names another computer is not switched off.

### On every system

- **A process number given to another program no longer reads as the program that stopped.** A lock, a claim or a hold left by a program that stopped no longer reads as held because another program was given its process number within the last minutes. A stopped round of **Improve Tia**, or a stopped move of Hoprig to another user, no longer blocks the next one when another program has since been given its process number. On macOS and Windows the dashboard now ends a go-live or check command left from before its restart at the command's time limit, and records the identity of the commands it starts. On Windows the start of a process Hoprig may not open (another account's, or a protected one) is read in a second way, so a lock it left is no longer held until that process ends.
- **The spending lock is taken over by one at a time.** When the lock of Tia's spending record is left behind, it is taken over after 5 seconds by one taker at a time, and that taker holds it at once, also at the end of its wait.
- **The offer to keep a way round is no longer left out.** The line that offers to keep a way round, after a command works right after the same kind of command failed, now comes also when the two ran within a moment of each other.
- **An upload past the size limit gets its answer.** An upload past the size limit that does not say its length is refused at once; the rest of what it sends is read and dropped for up to two seconds before the connection is closed, so the browser gets the refusal instead of a cut connection.
- **A clone with a file in its way is refused and said.** When a file stands where a folder on the way to a project's place goes (on Windows a link a repository brings can be checked out as a plain file), nothing is cloned, a line names that file, and the run goes on with the next project, where it stopped with an error before.

### For contributors

- **The test suite passes on GitHub's Windows runners.** With Node.js 24 and 26, about 835 tests are skipped there, each with its cause: mostly a stand-in that is a shell script, or a part that does not exist on Windows (Hands-off, the box). The Windows jobs still do not block a run, and the stand-ins that keep a test away from the real programs of a computer are not proven on a real Windows computer: run the suite on Windows only on a machine you can throw away, as GitHub's runners are.
- **The test runner says when a file's results did not all arrive.** A file whose summary never came is run once more on its own, and the runner says how that run ended; its closing line no longer says that every result arrived when that was not checked.

## 0.3.5 (25 November 2026)

This version needs Node.js 24.13.1 or newer. Tia installs, discards or takes back a skill learned from your own work, each by a card that waits for your tap. Bringing in a project you already have keeps a project that is laid out as it is, leaves installed packages out of the copy and takes the name you give. The workspace can tell you once a day what exists only on this computer, and once a week whether each repository is still on its git server. There is an Android kit, a restart of the dashboard from Health, and a first set of fixes for Windows, which is not supported yet.

### What changes when you update

- **Hoprig needs Node.js 24.13.1 or newer.** Node.js 22 is no longer supported, and 24.13.1 is the first release of Node.js 24 on which every test of Hoprig passes. On an older Node.js, `hoprig` says in one line which version it needs, which one this computer runs, and the line that updates it: `curl -fsSL https://raw.githubusercontent.com/allswebtech/hoprig/main/install.sh | sh` (on Windows `irm https://raw.githubusercontent.com/allswebtech/hoprig/main/install.ps1 | iex`), which installs the newest long-term release of Node.js and Hoprig with it. `hoprig doctor` shows the same as a cross with that line. The installer says which Node.js it found and puts the newest long-term release in its place, for you only. The tests now run on Node.js 24 and 26.
- **The code editor's package is updated.** The built-in editor (monaco-editor) goes from 0.57.0 to 0.58.0, which brings a newer DOMPurify (the library that cleans the HTML of a hover or a suggestion's details before it is shown): the five notices GitHub showed for it on the repository are closed. From this version the editor shows no remote image in such a text. Nothing else about the editor changes; `hop update` installs it.

### Health

- **Restart the dashboard from Health.** Computers → a computer → **Health** has **Restart the dashboard** where the dashboard runs as a background service, so a restart no longer needs a terminal. Its sheet says first what happens to the sessions there: kept by tmux (a program that keeps terminals running when the dashboard stops), they go on; in the built-in terminals they end, and come back only if "Reopen sessions after a restart" is on. Only your own page can press it, never Tia or a token; her card still restarts the dashboard only after an update.

### The App

- **Keys for the session list, and the keys a browser keeps.** In the App (the dashboard's chat view of a session), Ctrl+Shift+] and Ctrl+Shift+[ open the next and the previous session of the session list, as in the Claude Code desktop app (on a Mac Ctrl+Shift+] and [, where the browser keeps Cmd+Shift+] and [ for its tabs). **Keyboard shortcuts** lists, under "Kept by the browser", the desktop app's Ctrl+N, Ctrl+W and Ctrl+Tab with where the App has them. Inside a window of the desktop, a key that the desktop takes for its own windows says so on its row.
- **The App answers a question an MCP server asks you.** An MCP server (a program that gives the coding tool more tools) can ask you for something, such as which project a ticket goes to. Before, the App left that question unanswered; now it is a card in the chat with the server's name, its words as plain text, its fields or the web address it asks you to open, **Send** and **Decline**. Only you answer it: no permission mode, Hands-off (Hoprig answering a coding tool's questions for you) or Tia does, and Home says only "An MCP server asks you a question".

### Tia

- **Auto says when it waits for a calm computer.** With Auto on, a ready task is not started while this computer is overloaded (a load above 1.5 per CPU, or little memory left). Until now nothing said so, and the task simply did not start. Now **Work → Activity** says that Tia (Auto) waits with that task and why, with the load and the number of CPUs, once an hour at most while it lasts, and the task starts by itself when the computer is calm.
- **Tia can install, discard or take back a skill learned from your own work, each by a card.** She reads the skills that wait in Skills → Learned and the ones installed from your work. - **Hoprig needs Node.js 22.11 or newer.** It was "22 or newer"; 22.11 is the first release of Node.js 22 that gets long-term fixes, and the tests showed that Hoprig does not run right on the releases before it. On an older Node.js, `hoprig` says so in one line and does nothing else, `hoprig doctor` names it, and the installer treats such a Node.js as missing and puts a newer one in. A computer set up by Hoprig has a newer one already; on another one, run the install line once more and it brings one.
- **Home and New session look different, and nothing is ended or started by the update.** On Home the sessions that have waited for more than 6 hours stand folded under one line. New session starts with the project and folds the other choices under one line. On a phone, New session, Work's main action and **Add provider** on the Providers page stand in the page head. The limit card has one main button. Computers, set-up and the lines in Work → Activity say "main computer" where they said "hub" (the `--hub` flag, the settings and the addresses keep their names). How long ago something happened, and how long a session has waited, is written out in days from one day on (2 days ago), where it said 2 d ago, and so is how long a computer has been on (up 3 days 5 h, where it said 3 d 5 h). See "Easier when you are not a programmer" below.
- **"Tia runs on: Automatic" means your subscription now.** Where you have a subscription sign-in for Claude Code, Tia thinks on the first one that can answer now (one she may use and that is signed in), and simply answers. Before, Automatic was Auto mode (Hoprig's way of moving a session to the next provider, the next AI account, when one reaches its limit) whenever Auto mode was on. When every subscription is at its limit she says so, with the time the first one can be used again, and she does not move to a paid provider by herself; where you let her use another provider, the notice offers **Choose another provider for Tia**, which only opens **Tia runs on**. With a provider you chose yourself nothing changes. With no subscription she runs on Auto mode or another provider only when it is one she may use (Settings → Tia, "Providers she may use"); when none of those can run her, she says so and names that place: tick one there, or choose one under **Tia runs on**. Settings → Tia shows what Automatic picked, for example "Automatic (now: Claude Max)".
- **Tia asks before she uses a provider billed by use, until you set a daily limit for paid use.** With her level at "Hands off" (the highest of her three levels, in Settings → Tia; a different thing from Hands-off, Hoprig answering a coding tool's questions for you) she started sessions on a provider with an API key, and wrote to them, without asking. Now each of those is a card until you set **Daily limit for paid use (US $)** under Settings → Tia. A move of a session at a usage limit by her limit rule or **Tia decides** at "Hands off" is one of those too: it needs the limit and counts against it, and so does a nudge or an answer **Tia decides** types into a session on such a provider (see "Tia can do five steps" below). So are a call of **Tia decides** and a look into what nobody can explain: they run on such a provider only at "Hands off", only when every provider she may use is one (Auto mode counts as one when its order holds one), and only within the limit, which counts what they cost (see "Tia can decide" and "Tia can look into what nobody can explain" below). With no limit set, the limit rule and **Tia decides** do not move a session onto a provider paid per use and do not type into a session on one: the item says so in one line and offers **Set a daily limit for paid use**. Where she herself would think on such a provider with no limit set, she does not answer: the notice names the provider and offers **Use <your subscription> (included in your plan)** and **Set a daily limit for paid use** (Tia, below). A provider you sign in to is not touched by this.
- **A Claude sign-in on a Console account now counts as paid use.** A Console account is an account that is billed for each use, not a subscription. Where Claude Code's own check of the sign-in finds that it belongs to such an account, that provider counts as billed by use: for Tia (her daily limit for paid use counts it, and so does a message she types into a session on it), for a part of a Lead session (a piece of work handed to a helper, see Lead model below), and for Auto mode. The Providers page names it "Claude sign-in billed by use (Console account)", and its own page calls it a sign-in, never a subscription. While **Also use pay-per-use providers** is off, Auto mode leaves such a sign-in out: its row in the order, and its row in the list while it has a place in the order, says "Not used while pay-per-use is off" (a pay-per-use API key's row says "Billed by use · not used while pay-per-use is off"). A session that already runs under Auto mode on a provider it leaves out is no longer served: its requests to the model are refused, with a line that says why; to go on, turn that switch on or start the session again under Auto mode. When nothing is left in the order that Auto mode may use, a start under Auto mode says "Auto mode has nothing it may use" and names each provider with its reason (billed by use while that switch is off, no longer there, or not serving Claude Code); a Work run on Auto mode then does not start and says the same, and Tia leaves such an Auto mode out (see "The Auto mode card names your own providers"). To use them in Auto mode, turn that switch on, on the Providers page (its help says that turning it on puts them at the end of the order); to use Auto mode without them, put a subscription into the order. **Use in Auto mode** on the page of a provider billed by use says before the press that it turns that switch on too, and the message after the press says that it did. A subscription sign-in is not changed.
- **After an update through the installer the dashboard runs the new version.** Set-up compares the running dashboard's version with its own and restarts the dashboard when they differ. Where sessions would end with it, it names them and asks first (the default is no; with `--yes` it does not restart and says how).
- **`hoprig serve` never leaves a second dashboard beside the first.** When its port is held by this Hoprig's own older dashboard, it says so, ends that one and starts. One of the same version is named and left alone (`--take-over` ends it), and any other program on the port is never ended.
- **The upkeep no longer touches a project.** The upkeep is the dashboard's own round over your workspace, on a timer. With "keep the workspace in step" on it keeps the AI brain, your groups' own repositories and the other repositories in step. A project is fetched, fast-forwarded or pushed when you ask: `hoprig sync <name>`, or Sync on the Workspace page. The upkeep still tells you about a project on this computer that has commits to push or to pull, read from what is on the disk. The first round after the update says this once.
- **Restore brings no project by itself.** `hoprig workspace restore --with-projects` brings them all, as before. A project that is only in the map is no longer "missing": it is "in the map, not on this computer", with `hoprig get <name>`.
- **`hoprig sync` and `hoprig drop` are commands.** A provider file named `sync`, `get` or `drop` can no longer be started by that name: `hoprig add` refuses those names and `hoprig doctor` names such a file with the way to rename it. It is never deleted. The same holds for `adopt` and `sessions`, two more commands of this version.
- **`hoprig rm <name>` asks before it deletes a profile** (a profile is a provider's settings file), and without a terminal it deletes nothing unless you add `--yes`. So do `hoprig tokens revoke`, `hoprig machines rm` and `hoprig workspace forget`.
- **Bypass permissions needs a switch in Settings.** Bypass permissions is the mode in which Claude Code runs every command without asking you. As in the Claude Code desktop app, the mode is offered only once **Allow bypass permissions mode** is on (Settings → New-session defaults; it asks first). A dashboard that already used bypass keeps it on and says so once on Home; a new install starts with it off.
- **In bypass mode a delete is answered by itself only in the session's own folder.** Hoprig's hook (the small program of Hoprig that Claude Code calls at each step of a session) answered a plain delete "inside the folder it runs in" by itself, and that folder was wherever the session's shell stood: also another folder the session was given (a project's need, "Also open", a folder added by hand). Now the shell must stand in the folder the session was started in, or below it; anywhere else the coding tool asks you, as it does for every other delete. Nor is a delete that would take away Hoprig's own settings, its state, its hook or its installed program, or a folder above one of them: Claude Code's own question stands for it. In an OpenCode chat in bypass mode, a delete inside the quoted command of a program that runs one (such as `eval`), after a variable (a name that stands for a value) set with `+=` before it (`X+=1 eval 'rm -rf build'`), is now your card, as it already was after `X=1`, and so is one after an element of a list (an array) set before it (`A[0]=1 eval 'rm -rf build'`, whatever stands between the brackets: a variable, quotes, a space, a sign or a command, `A[$i]=1`, `A["k"]=1`, `A[i + 1]=1` or `A[$(id -u)]=1`), and one after a value, a host or a user written with a variable (`X=$HOME/out eval 'rm -rf build'`, `ssh ${HOST} 'rm -rf build'`); before, the chat answered it by itself.
- **Automations moved into Work → Schedules.** Your schedules run as before, on this computer; the old address opens the new place, and the pause switch is under Settings → Automations → Advanced.
- **The dashboard looks at more by itself.** For the new Operator page it reads, about once a minute, this computer's load, disks and processes, whether each gateway (a program that passes a coding tool's requests on to a provider) answers at its port and its own login page (and the public link's, while the link is on), and once in five minutes the git state of the workspace's repositories: no fetch, no lock taken, nothing written. It starts no model and changes nothing; a step is done only when you tap it, or by one of Tia's rules, **Tia decides** or her looks once you switch them on (Operator, below).
- **Ctrl+B in a session's terminal on the page goes to the program**, like every other key. tmux (a program that keeps terminals running when the dashboard stops) has commands of its own (Ctrl+B and a key); they are for a terminal of your own (`tmux attach`), not for the page. A page that was open during the update keeps working; reload it once to get the new key handling. A session started before the update shows its program's title after it is started again.
- **Shift+Enter opens a new line in a session's terminal.** A terminal in a browser sends the same byte for Enter and for Shift+Enter, so Claude Code sent the message. The page now sends a line feed for Shift+Enter, which Claude Code reads as a new line; the key bar on a phone has a **New line** key.
- **`/exit` just exits.** A session you end yourself in a terminal (`/exit`, Ctrl+D, Ctrl+C twice) no longer shows the menu of profiles: the terminal is back at its shell, with one dim line on how to continue it later. The menu stays for a session that stopped at a limit, a provider's error or an error code.
- **An App session asks its provider for a short title, once.** After its first reply a Claude Code session in the App (the dashboard's chat view of a session) that has no name yet sends one small request (about three thousand tokens) to the session's own provider, as Claude Code does in a terminal, and is then named by that title. Settings → New-session defaults → **Name sessions with a short title** turns it off.
- **What you delete in the App goes to a trash for 30 days**, then it is removed for good with its transcript. Nothing is in the trash after the update.
- **Tia does nothing by herself after the update.** Her rules on the Operator page are off, and so are **Tia acts by herself** and **Tia decides**. All of them are off after a new install too; nothing changes until you switch one on. One small file is new whatever the switches say: `runs-ended.jsonl` in the state folder (where Hoprig keeps its own records on this computer) notes, for one day, which provider a session was on when it moved to another or ended (the conversation's id, the coding tool, the provider's name, the time; no path and no text).
- **A session Tia started asks you before an act that is yours alone.** Until now a session she started for you in a mode without questions ran an administrator command, a push to the main branch and the like as any session of yours would. Now such an act in a session SHE started (a terminal session, a chat, a task she starts for you, a goal, a schedule she added) is held as your card, also while Hands-off is off, until you give her Full administrator rights on that computer. At Full most of her administrator commands run without a card, and these stay your card at Full too: a release or publishing, a direct call to GitHub or GitLab that can change something there, a pull request, a push to the main branch or a tag, a push that deletes branches, a merge into the main branch, a push or a merge Hoprig cannot place or check, a delete outside the session's folder, a deploy, a change to project.json, a command that touches Hoprig's own files, and a command Hoprig cannot read (an administrator command too). Which commands these are is read the same way as for Hands-off (see the section "Hands-off" below). A session you start yourself is not changed. Her administrator rights are **Off** after the update, and with Off an administrator command she is asked to run herself is refused with no card. Also refused, where until now it was a card, is a command you ask her to run that is a push or a merge, a system service or package tool, a global npm install, a connection to another computer or a request that sends data out (each read by the command's first word, also after another command joined to it), and a command Hoprig cannot read; she gives you the command to run yourself. Behind another program (`timeout 60 git push …`) such a command is still a card.
- **Tia starts a Codex or OpenCode session only at Full.** Hoprig has no hook for those two coding tools, so nothing could hold such a session of hers. Below Full, so after the update, she does not start one: she says so and uses Claude Code. A Codex or OpenCode session you start yourself is not changed.
- **A chat of the App tells Hoprig how it stopped.** Hoprig's hook now also runs on four events of a chat (its start, your message, its stop, and a stop by an error) and writes only how a provider stopped the chat or an agent of it; the chat's status and its cards stay the chat's own. The Operator's look reads those records too. Nothing asks a provider by itself.
- **The dashboard writes one small file when it starts:** `dashboard.json` in its state folder (readable by you only: where it listens, its process number and a key), so that `hoprig setup` on the same computer can ask the running dashboard where it listens (`GET /api/local/facts`, answered only with that key). It goes again at a stop. The update itself closes nothing and rewrites no service file: on a server, a dashboard that was left open to the network is closed by `hoprig setup`, after your yes.
- **Hoprig notes how its own work went, on this computer only.** At the end of `hoprig get`, `drop`, `setup`, `pc setup`, an update and a `hoprig doctor` with a cross, one small file is written into the state folder (`field/reports/`, the newest 50, each under 1 KB): the kind of work, whether it went well, the class of what went wrong, the steps, the version and the system. No name, path, host, address or key is in it. Nothing is sent anywhere: sending is off, and there is no address until you set one.
- **The Operator's look reads more, and keeps one small file.** It now also reads Claude Code's own records (read only, a bounded part per look), so that a session you ran outside Hoprig is seen when its provider stops it, and it keeps `operator/conversations.json` in the state folder: the conversations Hoprig ran in the last day. A provider's `MODELS` rules rename models for Auto mode only, as before, until you turn on that provider's new switch.
- **Missions are off after the update**, with their master switch and every project's own switch, as after a new install. One small thing runs whatever the switches say: every 15 seconds the dashboard lists Work's `missions` folder, and with no mission of its own going it stops there.
- **A mission's choices, the looks and your corrections are off after the update.** They are off after a new install too. With the three switches off nothing of them starts or is written. One small read is new whatever the switches say: the dashboard reads the looks' one record file (`look-record.json` in the state folder) to clear away a look that was lost when a dashboard stopped; with no such look it writes nothing.
- Nothing of yours is removed or moved by the update. A computer still on 0.3.2 that shares the AI brain keeps working.
- **Installing or updating a gateway, and a Fix, need your confirmation that names the computer.** The pages send it after your yes. A request without it is refused, and Tia no longer does any of the three by herself: she proposes a card that you confirm.
- **A gateway's start also gets `HOST=127.0.0.1`** on a server and where the dashboard listens on this computer only, beside its definition's own words as before. A gateway that already runs is not restarted by the update: stop and start it once (under Gateways in its computer's Health) and it follows the rule too.
- **Hands-off is offered, and nothing of it changes until you turn it on.** No project's switch and no session's switch is on after the update, nothing is answered for you, and a session open during the update keeps behaving exactly as before — its hook neither holds nor answers. To hide it, set `handsOff.offered` to `false` in Hoprig's settings file, `config.json` in `~/.config/hoprig`.
- **A session that stands at a question of Claude Code itself is under Needs you.** Before it starts, Claude Code can ask something of its own (whether to allow imports from outside the project, its once-only question about Bypass permissions, another numbered choice). Such a session read "Starting" and seemed to hang. Now its card says in plain words what is asked, which answer is the safe one, and **Answer** opens its terminal. Nothing is answered for you. In a job Tia started she no longer answers such a question either: she tells you, the job waits for you, and any key she would press there is a card for you at every level.
- **Get started's git step is done when git is set up**: your name and e-mail, GitHub signed in, the AI brain kept on GitHub (or another git server) and linked to it. It was open again whenever the AI brain had a change. Changes of the brain are now a line of their own in the Git and GitHub panel, with a button.
- **Hoprig's record of your own skills moves out of the AI brain.** The small file in which Hoprig notes which skills it installed for you (`.hoprig-skills.json`) was written beside them, and that folder is often your AI brain: every set-up and update left a changed file there. It is kept in Hoprig's state folder now (`skillhub/user-skills.json`). A file an older version left in the brain is still read, and Hoprig never deletes, moves or commits it. A project's record stays in its own `.claude/skills`.
- **The first commit Hoprig makes leaves private folders out.** When it starts the AI brain or a new project in git, folders named `no-ai`, `ignore` or `ai-ignore-dir` and installed packages are not in that commit, so **Keep on GitHub** does not upload them. A private folder you want in git stays yours to add.
- **A provider that keeps its sign-in in a folder of its own is no longer shown by the default sign-in's state.** Its row said Signed in or Not signed in from the default folder, and its Sign in and Sign out buttons acted on the default folder. Now its state reads as not known, those buttons are gone for it, and its page says how to sign it in (a terminal session on that provider, then `/login`).
- **The quick messages under a terminal start with two fewer.** On a computer where you never changed them, `/compact` and `/model` leave the row (continue and `/clear` stay); a list you saved yourself is kept as it is. Both are one line away in Settings → Quick messages.
- **A session whose coding tool ends at its start says so.** When Claude Code, Codex or OpenCode ends with an error within ten seconds of a start you made, the session's card reads "did not start" with what the tool printed last, where it showed an empty terminal before. For this the launcher writes one small note beside the run's record (readable by you only); a note older than a day is removed.
- **Under root, bypass permissions is not offered.** Claude Code refuses that mode for root (the computer's administrator account), so a session started with it ended at once. A dashboard that runs as root no longer offers the mode or starts a session with it: it says why and names the way out (Settings → **Runs as root**, or `hoprig move-to-user`). An ordinary user sees no change.
- **The installer run as root asks before it goes on.** As root, `sh install.sh` now makes an ordinary user named `hoprig` and sets Hoprig up for it, after one yes (a question on a terminal, or `--yes`); `--stay-root` keeps Hoprig on root, as before. With no terminal and no `--yes` it makes nothing and names the two commands. `HOPRIG_YES` in the environment is no longer a yes for root.

### Easier when you are not a programmer

- **Get started: every open step has its own button**, not only the next one, and the phone step comes before Skills.
- **The AI brain is saved from the page.** The Git and GitHub panel says "4 files are not saved to your git server yet" with **Save them**. A sheet names the files and where they go; nothing is saved before **Save and upload**, which runs as a job with its output. It gets the server's newer changes first, and when the brain here and on the server have both moved it says so and does nothing. A file that looks like a key or a password is refused by name, and so is a file over 50 MB (it cannot be checked); every file can be seen first; a private folder is never listed or uploaded; only the files the sheet showed are taken. A brain whose branch is not linked gets **Link it**, a brain that is not in git yet gets **Keep on GitHub**, and every place a row names can be opened from that row.
- **A turn the AI account refused says so in a plain line**, with the button that fixes it where one press on this computer can (sign in again), a line of its own when the credit is used up, and the coding tool's own text under Details.
- **Add a computer starts with "A laptop or another computer of yours"**, and each way says which computer it is for. The SSH way takes a key file on the page instead of `ssh-copy-id` in a terminal.
- **A new project's name may be typed as you say it**: "Bakery Website" becomes the folder `bakery-website`, shown while you type. Only a name with nothing usable in it is refused.
- **A sentence that names a switch opens it.** Home's note about Bypass permissions, the queue line under Work → Schedules and the sign-in code's line open Settings at that switch, in view and focused. The switch is never pressed for you.
- **Plain words where there was a system error or nothing:** a task list that cannot be read ("Hoprig could not read your task list", Try again, the error under Details); a computer that does not answer ("cannot be reached", with a link to its page); a wrong password on the sign-in page (a device that is signed in can show a sign-in code); `hoprig doctor`'s Claude sign-in line (it also names Home → Get started → Sign in to Claude).
- **Work: a task row's play icon is a button that says "Do it".** A screen reader hears the task's title with it.
- **"This link is mine" is a button.** Where a project's folder is a link you made yourself, the page had a command to copy. Now a sheet names the link and where it leads, and **Yes, it is mine** records it. Only the place the sheet showed is recorded: if the link leads elsewhere by the time you press, nothing is saved and the sheet says so. A link to your home folder, the workspace, the projects folder or a folder above them is refused.
- **"Move it out", when a save finds a file that looks like a key.** The save sheet names the folder beside the AI brain where such files go (`ai_brain-moved-out`), and **Move it out** moves exactly the files the sheet showed, each keeping its path. Nothing is deleted, and a file already there is kept (the new one gets " (2)"). For a file git already keeps, the sheet says that it leaves the git server at the next save, that its old versions stay in the history, and that a real key must be changed. Then the same sheet offers **Save the rest**.
- **Adding another computer starts with the install.** The line to paste on the other computer begins with "Install Hoprig on the other computer first, if it is not there yet." and a link to the install page; the fingerprint and the `hoprig join` command are folded under "For the terminal".
- **Providers shows what a gateway is started with** when its program is missing, on the page, where it said to look in a terminal.
- **Get started.** The phone step's button reads "Show a sign-in code" and opens the code at once; a second code does not end the first, and the sheet says so. The Skills step says what a skill is and has **Switch on**.
- **A chat's first screens.** An empty chat asks for your own words. The panel's head reads "Where it works", and a folder with no changes says "No changes yet since the last save point". On a first chat Ultracode and Lead model are behind **+**. The first message of a new project is folded as "Hoprig asked the AI to set up <project> from your brief", with the full message one press away and your brief under it.
- **Work.** A new task takes the project when there is only one. The Do it sheet folds folder, coding tool, provider, model and effort under one line that says what is chosen. A schedule and a run by the AI say "in a separate copy of the project". The band over the list says "Your list is saved on this computer" and offers a copy in your AI brain only where the brain has a git server. The plan sheet names what is still missing beside its button. On a phone the tabs are one row that scrolls sideways.
- **On a phone and on a wide window, what you need stays in view.** Home's line over the old waiting sessions stays below the page head when the page scrolls to it. New session on a phone keeps a whole project name beside **Continue**, on two lines where it needs them, and has no empty band around **Also open**. On a phone a new chat with Tia says "New chat started." right above her message box, where nothing said it before. On a wide window Tia's round button stays beside the page's column instead of at the window's edge. A short message at the edge of the page puts its button under its sentence when both do not fit, and a long word in it breaks, so it is never wider than the screen; on a wide window these messages start under the page head, so its buttons stay free; a tap on such a message closes it, and its button is outlined. The page head is solid, so the page's text never shows through it. Setup's line on why git is not set up wraps whole on a phone instead of being cut, and so do the lines under a computer's controls on Advanced and under Setup's link to the workspace folders.
- **A new project's check step opens with one line** ("A folder bakery-website with your brief and the starting files the AI needs (35 files). Nothing else on the computer changes."), with the list under "What exactly"; and **Sign in to GitHub** opens over the step, so the name you typed is still there when you come back.
- **Settings.** An address that names another page opens that page; one that names no page says "This settings page does not exist" with a way to all settings. The list reads "Security and sign-in". The public link's Temporary card says who carries the link and that its address changes at each start.
- **More sentences that name a place open it**: 23 lines on the pages that said "Settings → …" or "on the Providers page" in words only are links or buttons to the exact control now.
- **The card for a first-time question of Claude Code names a key only when the screen shows it.** The number of the safe answer is read from the question as it stands on the screen; where its line shows no number, the card says which answer to choose in the terminal and names no key.
- **Plain words.** "Provider" is said once in plain words where you meet it first ("The AI account this chat runs on"), and Context's tooltip says "how full the chat's memory is".
- **Old waiting sessions are folded, and "End them…" ends the ones you tick.** Under "Waiting for your next message" the sessions that have waited for more than 6 hours stand under one line (**Show** opens it). **End them…** opens a sheet that lists each one with its computer and how long it has waited (7 h, 2 days), each ticked, and one button says the number ("End 5 sessions"). On your press, and only then, each ticked session's program is ended as **End session** in its menu does; a session that changed in the meantime is left and named ("it started working again", for example). The result stands in the sheet, under the title "Sessions that had waited", or in a short message at the edge of the page (a toast) when you closed the sheet before the press ended. Its conversation is kept and can be continued from the project's page. A session whose command still runs in the background, or that has a card, is never folded, and App chats are not in the sheet.
- **A question can be answered on its Home card.** A session that ends in a question has a reply box on its card. It sends only on **Send** and only to that session; a permission card has no such box. Just before it sends, the page reads the session again and sends nothing when the session now works again, asks something else or has ended. Then the dashboard types your words only while the session still waits and no question stands on its screen, and presses Enter only while it still waits: when a question came up between your words and their Enter, the words stand typed in the session, not sent, and a toast says to look at the session before you send again. On another computer whose Hoprig is older than this dashboard, only the page's own check just before it sends stands. When nothing was sent, a toast says why and your words are kept: they stand in the box again while the session waits for your answer. Where the toast names the session, it uses the title on its card, in quotes, and it says to open the session to see what it does now.
- **A permission card says what will run.** "Claude wants to run: …" with the command, **Allow, and don't ask again for this kind of command**, and under the buttons which commands that lasting answer covers ("This kind of command: npm install"). After your answer the card stays for a second as done and a toast says that the session goes on. A session at the coding tool's own first question reads "Asks you first", and its card says that the question is asked in the tool's own window.
- **The limit card has one main button.** The first account that costs nothing more is the main button; the other ways stand under **Other ways**, and each paid one ends in "· costs money per use". Auto's button reads "Go on with the next provider that has room each time" and no longer calls a paid provider free. The near-limit line names each provider once, and no longer names a paid provider as the way on while a free one is there. Neither names as the way on a provider that is itself almost used up (90% of a limit or more), and over several computers Home names a way only when each computer would take the same one, else it says "another provider".
- **New session starts with the project.** The other choices are folded under one line that says what will be used ("On Workstation · in the App · with Claude Code", **Change**). ### The workspace

- **Which computer has what, on the Workspace page.** Every place of the workspace (the projects folder and each group) with what is here and what is only in the map, "Last here", and for each of your computers what it has, read from the brain's own files: "as of" a date for another computer (marked old after seven days), "unknown" for one that has written none. One reader gives the same to `hoprig workspace status --all --json` and `hoprig get --list --json`. A computer listed under Computers by another name than its workspace label is joined by the label it reports; where it reports none (an older Hoprig there), both names are said, and nothing is joined by a guess.
- **Drop a project from the page.** The sheet shows what the check found: what would be pushed first and what would be removed. It is good for one press within ten minutes, and you type the project's name. What a press pushes is exactly what its check showed: when a file changed meanwhile, also during the press itself, nothing more is pushed, the answer is "changed", and the sheet is drawn again. It is the same drop as `hoprig drop`. Its commits hold exactly the bytes the check showed, so a repository's own commit hooks do not run for them and they are not signed.
- **Only your own page may do what is yours.** A drop, adding or taking out a group, writing the workspace's rules, Sync with push and the brain's push are accepted from the dashboard's own page (also from your main computer's page, relayed), never from a script's token, from Tia's door or from another site. A main computer that runs an older Hoprig is told to update first.
- **Groups on the page.** "Add a group" runs dry first and its confirmation names what goes into the map; "Take out of the map" leaves the folder where it is.
- **Tia knows the workspace.** She can say where a project is and which computer has it, check a drop without changing anything, and open the page's sheet for a drop or a new group, filled in, for you to confirm there. She cannot drop, take out a group or write the rules. Her instructions tell her to say so when a project you name is not in this computer's workspace, and where it is when another computer has it, before she asks you or prepares a start there for your tap. Her tool list stays at 25.
- **A project can name what its sessions need to read, and you say yes on each computer.** A project's `project.json` may name other folders of the workspace as `needs` (a shared kit, a docs project). A session of the project then gets them as extra folders: its file tools may read there and not write, and a private folder inside a need (`no-ai/` and the like) is never entered, by any path, also not through a link. A need is opened only after you allowed it ON THIS COMPUTER: at `hoprig get` (its one question, or `--with-needs`), with `hoprig workspace needs allow <project> <need>` (`needs list` shows them, `needs revoke` takes it back), or with **Allow** on the project's page and in the new-session sheet. A need that is named and not allowed is said at the session's start, with the command, and not opened; one that is not on this computer is said with `hoprig get <name>`, and nothing is fetched by itself. A need whose tree holds a link leading out of the workspace is not opened (unless the link is one you named with `hoprig workspace mylink add`), and one too large to check within five seconds is not opened either. **Also open** in the new-session sheet, and `--with <name>`, open another folder for that one session; that is your own word and needs no second yes. More in `docs/WORKSPACE.md`.
- **Each computer has a label and a file of its own in the AI brain** (`computers/<label>.json`): its Hoprig version, which entries of the map are on it, and the four folders that are not in git, in names and counts only (never a path, a host name or a key). Only that computer writes its file. Set-up asks for the label once; `hoprig workspace label <name>` gives it later. The Workspace page and `hoprig get --list` show which computer has what.
- **The map keeps itself between two computers.** With "commit the map" and "upload" on, two computers that add different projects in the same hour no longer leave you an AI brain that "moved on both sides". When the only difference on this computer is Hoprig's own save of the map, or of the brain's memory folder, Hoprig unites the two maps by its own rule and uploads the result. Only what this computer added since the two parted goes into the map: a project or a repository you removed or renamed in the map on one computer is not brought back by another computer's older map. It never merges text and never forces, and it stops with the reason when anything of yours is in the way: a commit of your own, a staged change, a file git does not track.
- **A clone that was cut off is cloned again.** `hoprig get <name>` and restore move a half clone aside under a dated name, never delete it, and say so.
- **Push my other branches** (off; one switch per place where projects live): the upkeep uploads committed work on a branch that is not the default one, so that a lost computer costs none of it. A default branch is never pushed by itself, nothing is ever forced, and a branch that was removed or moved on the git server is said, not pushed back.
- **Set-up has one path for the workspace**: an AI brain with a map found on your GitHub account means one question, then restore; none found means one question, then a new one.
- **The brain's memory folders** can be committed by the upkeep too (`hoprig workspace auto --memory on`).
- **The credentials folder can be a private repository of its own, when you choose it** (`hoprig workspace credentials --repo <address>`, or `--github [<name>]` for a new private repository of your account). The cost is said once and you confirm by typing the repository's name; no option skips it. It is all or nothing, Hoprig never makes the repository public and never pushes to one that is public (GitHub is asked right before each push), and nothing in the folder is ever named in what is said: counts only. The map then names it, and restore clones it right after the AI brain. Off by default: the folder stays a local folder. An upkeep switch, also off, commits and pushes a change of it by itself (`hoprig workspace auto --credentials on`).
- **Where a push of the credentials goes is asked of git itself**, in the same environment the push runs in. A rewrite rule (in a settings file or in the environment) that sends the address to another owner, another name or another server is refused, and so is an address in a shape Hoprig does not know for certain (it is never taken for a folder on this computer) and a remote that a helper program pushes.
- **Credential links.** A project says in its `project.json` which file or folder of `credentials/` it sees and under which name (`"credentials": { "code/shop/.env.local": "shop/shop.env.local" }`); `hoprig get`, restore with projects, `hoprig project setup` and `hoprig workspace link` make the links, relative ones, only in a place git ignores; the workspace's status says which wait, are missing or broken.
- **`hoprig drop <name>` takes a project off this computer, safely.** Only when all of it is on its git server, so that `hoprig get <name>` brings it back; another computer having it does not count. It fetches, checks every repository in the project's folder and asks before anything is done: work not committed can go to a new `wip/` branch and be pushed, commits on a default branch are pushed only on your yes, and files git ignores that cannot be made again (an ignored `.env`, key files, `test-data/`, a private folder with its file count) are listed one by one and deleted only when you type the project's name. Without a terminal that drop is refused, with the list. `--check` says what exists only here, `--dry-run` every step; both change nothing.
- **What a drop removes without asking is three things, decided in one place**: a folder a build or an install makes again that git ignores as a whole (`node_modules`, `build`, `.venv` and the like), a credential link that `project.json` names and that points where it says (`get` makes it again; the credentials folder is never touched), and `.DS_Store` or `Thumbs.db` as a plain file. Everything else is on the list.
- A drop that was cut off is finished or shown by the next `hoprig get` or `hoprig workspace status`: the folder waits under a dated name, and when some of its parts still have their git folder, the words name those parts so that what is only there can still be pushed. Nothing of drop runs by itself.

### A computer that already has projects

Projects inside an untracked folder are named.

### Hands-off (off until you turn it on)

- **A switch that lets Hoprig answer for you.** Turn Hands-off on for a project (Settings → Hands-off) or a session (its menu) and Hoprig answers some of the coding tool's questions with yes — the option the tool marked as recommended, or your note for the project — so the work does not wait for you. It uses no model. In a session's menu, the line under **Turn on Hands-off** reads "Hoprig answers what the tool marks as recommended, or with your note". It is off until you turn it on, on every project and every session, after an install and after an update. The first time you turn a switch on in a browser, a sheet, **What Hands-off does**, says what it answers: a question for which the tool marked no recommended answer gets your note for the project as a written answer, where you wrote a note and the tool takes a written answer; otherwise it waits for you; a plan in the App is approved and the session keeps the mode it had; a plan in a terminal waits for you. It also lists what stays yours, each in one plain line, and how to stop it. **Read the first-time summary again** on Settings → Hands-off opens it again.
- **What stays yours in every case.** While it is on, a command of a kind that is yours alone is still held as your card, in every permission mode: administrator rights, a release or publishing, a direct call to GitHub or GitLab that can change something there, a pull request, a push to the main branch or a tag, a push that deletes branches, a merge into the main branch, a deploy, a delete outside the session's folder, a change to project.json, a command that touches Hoprig's own files, a push or a merge Hoprig cannot place or check, and a command Hoprig cannot read. A No never runs it; a Yes runs it once; nothing runs while a card waits. Hoprig reads a command as it is written, so it holds these kinds in the forms it can read, and a command whose program it cannot read. It does not know the value of a variable (a name that stands for a value given elsewhere) among a command's words, so such a word can hide a kind it would hold. It is a help against a mistake, not a fence around what a program does by its own code. It holds them also in these forms: a push whose destination or branch is a variable (`git push origin $BRANCH`), a push that deletes a branch by name (`git push origin --delete feature`, `git push origin :feature`), and a push of the branch the session is on (`git push origin HEAD`, also with the branch written after the remote as `$(git branch --show-current)` or `$(git rev-parse --abbrev-ref HEAD)`) while that is the main branch; more ways to publish or release, or to change a release that is out (`gh release upload`, `gh release delete`, `poetry publish`, `npm unpublish`, `npm deprecate`, `mvn deploy`, `./gradlew publish`, `docker buildx build --push`, among others); a call with `gh api` or `glab api` that sends a change (one that names a method, the kind of request, other than GET or HEAD, the two that only read; one that sends a field and names no method; or one that sends a file with `--input`), and such a call to the GraphQL address whatever method it names, also written as a path or a full address (GitHub's and GitLab's one address that takes questions and changes alike, so the method named does not tell them apart), or written with a variable that may stand for that address in a call that sends a field (`gh api -X GET "$EP" -f query=x`, `"$BASE/graphql"`); and a deploy script started by the program that runs scripts of its language, such as Node or Python (`node scripts/release.mjs`, `python3 deploy.py`, also after that program's options), or a deploy task of a program that runs a project's named tasks (`rake release`, `just deploy`), as when a shell runs the script. These go through: a push of the branch the session is on, in those forms, while that is not the main branch; a `gh api` or `glab api` call that names GET or HEAD, also with fields, and is not to the GraphQL address, also where a variable is the value of a field or a header or stands in a path whose written text names something else (`"repos/$OWNER/$REPO/issues"`); a plain read of an address written with a variable, with no field; a script that writes release notes (`node scripts/release-notes.mjs`); a test file run the same way (`node scripts/release.test.mjs`, `python3 deploy_test.py`); and an everyday run whose later word only happens to be release or deploy (`node --inspect dist/server.js release`).
- **Hoprig's own folders are found however the path is written.** A command that reads, moves, writes or deletes in Hoprig's settings or state is yours while Hands-off is on. It is recognised also where the path is written with a doubled separator, `.` or `..`, quotes or `$HOME` (`mv ~//.local/state/hoprig …`); where a wildcard (`*`, a pattern that matches many names) or a list in braces could name one of those folders or a folder above them (`cat ~/.config/hop*/config.json`, `~/.config/{hoprig,other}`); and where a short path follows a change of folder (`cd` or `pushd`) to a folder Hoprig can tell (`cd ~ && cat .config/hoprig/config.json`); after such a change, a move or a read of a folder that holds them is held too (`cd ~ && mv .config old`). After a change of folder Hoprig cannot tell (`cd $DIR`, `cd -`) the short path is not followed.
- **A command of yours is found behind the program that runs it.** An administrator command, a push to the main branch, a release or a deploy is held also where it stands behind another program (`timeout 60 sudo …`, `nice "-n" 5 sudo …`, `if sudo …; then`, `strace … git push origin main`), behind a variable written in quotes (`VAR="a b" sudo …`), behind settings of a variable and names of files to write to in any order (`x=1 2> err.txt sudo …`), behind a program that fetches a tool or sets up its environment and then runs the command (`npx`, `pnpm dlx`, `uv run`, `poetry run`, `bundle exec`, `cross-env`, `dotenv`, `python -m`), or inside the text a program is handed (`flock lock -c "sudo …"`, `env -S "sudo …"`). `run0` and `machinectl shell` count as administrator rights like `sudo`, and so does `systemd-run`, unless it runs the command among your own user's programs on this computer (`--user`, with no option that reaches another computer, user or group or the system's own programs, and no option Hoprig does not know). Where Hoprig cannot tell with certainty which command a program would run, the command is yours: so is a command whose program is a variable (`$PROG`, `"$EDITOR" notes.txt`), alone, after another command or after a name of a file to write to, a program whose name has a variable behind text (`./run-$TARGET.sh`, `bin/tool-$NAME --help`), unless text with a `/` after the last variable writes the name out (`bin/$TOOL/run`), and a program that is the output of another command (`$(…)` or a backtick). An ordinary command that only names the word (`grep -rn sudo docs`, `git checkout release`) is not held, and neither, as a rule, is a variable among a command's words or in the name of the file it writes to (`echo "$HOME"`, `npm test > "$LOG" 2>&1`), nor more text behind a variable in a setting before the command (`FOO=$A$B npm test`, where the program after it is still read), nor a word handed to a program as its input (`cat <<< "$X"`); a push, a delete and a path into Hoprig's own folders (`$HOME/.config/hoprig`) are still read for what they are.
- **How to stop it.** The same switch turns it off, and a session has its own Off. Three answers in a row with no work between them, or ten within an hour, stop the answers on their own; the hold stays until you turn the switch off. The full rules are in `docs/HANDS-OFF.md`.

- **Plan with AI.** You write the goal in your own words and name the project. A session researches it and comes back with a proposal: a note and a plan with milestones and tasks. Nothing exists in your repository before you press **Accept**; you can take tasks out first, plan again, or dismiss it. The session's answer is read strictly, as data: a note with HTML outside a code block, an image, a character that cannot be seen, or a link whose words show one address and that leads to another is refused, with the reason. It opens on your default provider, also before a project is chosen, so the provider is never left unchosen.
- **`hoprig tasks plans`** and **`hoprig tasks plan <id>`** show the plans in a terminal.
- **The bundled skill `plan-work`** is the method the planning session follows.

### Work: repeating tasks and schedules

- **A task can repeat**: every day, every week or every month (a monthly one on a day the month does not have falls on its last day). A repeating task keeps one open occurrence: when you finish it the next one is made, and a date that passes while it is still open moves on (the last ten missed dates are kept).
- **Run by AI at a time.** A task can name a time, a computer and a provider. At that time, on that computer only, a session does it by itself, in a branch and a folder of its own and never on the default branch, with a time limit (30 minutes unless you say otherwise, at most four hours). The task then waits for you in review with the answer, the commits and the changed files; accepting stays yours. It asks before a step unless you chose otherwise for that task, and tells you only when there is something to report, unless you want every time. One such run at once unless you raise it (up to four); a project that is not a git repository is refused.
- **Work → Schedules lists your schedules and your repeating tasks together.** A schedule can name the computer it runs on; when that computer cannot be reached the run is missed and said so, never run somewhere else. `hoprig tasks schedules` shows them in a terminal.

### Work: progress, a true estimate, and being told

- **Progress is read, never told by a model.** For every run of Work, every session that works and every schedule: when it started, its steps where the coding tool's own records name them (a workflow's steps done and to come, its agents), its last progress, and what it used where the tool reports it. Today shows one line ("6 running · 3 wait for you · 2 done · 1 failed"), a task's Runs sheet shows it, and so does `hoprig tasks progress [--json]`.
- **An estimate only from what was measured.** For a kind of work the time of the last finished ones of that kind is the basis, and the basis is always shown ("about 5 h 30 to 8 h 30, from 4 like it"); with fewer than two finished ones, Tia and `hoprig tasks progress` say "no time estimate yet", and Work's Today says it once under its count, with the reason that nothing like it has finished here, while each such running row says only when it started. No model writes or changes a number.
- **Being told, by code.** Settings → Notifications has a short list, each item on or off: something finished and waits for your look; something went live; something failed or stopped, with why; something has waited for your answer longer than a number of minutes; and a digest every few hours while work runs. Each message fits a phone's lock screen. One message per event, also across a restart; quiet hours; what happened while the dashboard was down is told once, as one message; a digest with nothing new is not sent. A message is never lost by a crash: one that was about to go is sent once more after a restart. Every item is off after an install and after an update, and your push address goes on working as before; with every item off, nothing of it runs, writes or sends.
- **Tia answers from the same lines.** "What is running", "how far is it", "how long will it take" and "what did you do tonight" are answered with the lines above, shown under her reply by code; a time or a count in her own words that the tool did not give hides her words for that turn, and only the lines are shown. With **Tia writes my digest** on (off by default) one small request words a digest in your language, and every number in it is put in by code afterwards. On a provider billed by use she words it only inside her daily limit for paid use (Settings → Tia), which counts it; with no limit set, or none left today, the digest comes in its plain form.

### Work: from finished work to live

- **Put together, checked, live on your tap.** On the Work page, the tab **Go live** takes a project's finished tasks through three steps. *Put together*: their branches are merged into one work branch in a folder of its own; a conflict stops it and names the two tasks and the files. *Checked*: the project's own check commands run on that exact commit, in a fresh copy of it, one check at a time on the computer; a tree that both passed and failed is not counted as passed. *Live*: on your tap the project's own update and verify commands run; "live since" is said only after the verify passed, and **Take back** returns to the tree before. The same as `hoprig ship status|together|check|allow|live|back|auto|drop <project>`.
- **A project's commands run only after your yes on this computer.** The commands are a block in the project's `project.json`; they are someone else's words until you confirmed them (the sheet shows them word for word), and a changed command asks again. Only your own page or your terminal may say that yes: not a token, not Tia's door, not another computer.
- **By itself only where you typed it.** A project's switch "go live by itself" turns on only when you type the project's name, never while a live command pushes or publishes, only inside the hours you set, once per tree, and never for a tree that also failed; "take it back by itself" follows a failed verify.
- **True after a crash.** Every step is written down before it runs; a step that was cut off is finished or closed at the next look, with the commands that did not run named, and a journal that was written by hand runs nothing. For Hoprig itself, a helper outlives the restart and takes a broken update back.
- **A restart waits for work in progress.** Where a go-live restarts the dashboard, running turns of App sessions are waited for and named; "Restart anyway" is yours to press. More in `docs/GO-LIVE.md`.

### Work: missions (a goal given to Tia)

- **A goal becomes a plan, and sessions she starts do the plan.** Give a goal on Plans or on the new **Team** tab, or ask Tia. Plan with AI proposes the plan, and nothing exists before you accept it. Then each task gets a role (developer, tester, researcher, writer, ops), the first free provider of your order, a model and an effort, and one session on a branch of its own, never on the default branch. A task the plan gives to you stays yours, and the mission waits for it.
- **Two switches.** A mission starts only while the master switch and the project's own switch are both on; with either off a goal is a plain plan proposal, as before.
- **A check owns "done", and a reviewer that did not write it reads every task.** When a session ends, code checks its branch: something changed, nothing is left out, and only the files the brief named. Then a reviewer session reads what the branch changed and says pass or fix; a fix goes back at most twice, then the task is yours. A reviewer's words are information for the fix, never an order.
- **A task's tests run in the box, by themselves.** When a task's session ends, the test command of the task's own project runs in the box (a task may name another project than its mission's; what to do next when it reaches a usage limit, or after it is sent back twice, is then decided for its own project too): no network, without your home, and able to write only to the task's own worktree. The dependencies come from the project's main checkout through a link Hoprig makes and takes away itself; nothing is installed. A folder the project says its sessions need is given to the tests only when nothing in it is denied to sessions. The card and the report say for each task where its tests ran and how they ended (passed, failed, stopped after the time limit, not run), with the last lines they printed. Files the tests leave in the worktree fail the check, and a review never starts over a file there that steers a session (`CLAUDE.md`, `AGENTS.md`, `.claude/settings.json`).
- **Your press on a task: "Run the tests in the box".** On a computer without a box the card says so and why, and offers only **Run them outside the box…**. That one asks again on a sheet of its own which says what it means (the tests run as you: they can read your files and keys, use the network, and change or delete anything you can), and it works only from your own page: Tia and another computer cannot ask for it.
- **A session of hers has the file tools only:** it can read and change files inside its own worktree, and nothing else. No shell, no git, nothing that reaches the network, no file outside its folder (also not through a link). It is started in Claude Code's own restricted mode, is not started at all where the installed Claude Code does not know that mode, and is ended at once if its own first line names another tool. The dashboard itself makes the one commit of what a session changed. A branch that changes a file which instructs coding tools (`CLAUDE.md`, `AGENTS.md`) gets no reviewer session: it is yours to read first.
- **Your limits hold:** sessions at once, working hours, the missions' own **Spend cap per day ($)** under Work → Team (each session gets a budget from what is left), a provider at its limit waits and says until when, and a subscription comes last. **Tia OFF** stops new starts at once.
- **Accept stays yours**, in Work, unless you name kinds that are accepted by themselves after the check and the review (only a task whose tests ran in the box and passed). A mission pushes and merges nothing.
- Each mission says what it cost in three numbers (time, tokens and dollars as the tools reported them), and a morning brief made by code says what happened since yesterday. More in `docs/WORK.md`.
- **A mission's session can run the project's tests while it works.** A session that writes or mends code for a mission had the file tools only: it wrote code it could not run, the tests ran after it had ended, and a failure cost a whole new session. Where the project has a test command and this computer has the box, such a session now gets ONE more tool: it runs your own test command in the box (no network, only the project's folder) and reads what it printed. It gets no shell and can run nothing else; at most 12 runs and 30 minutes of runs a session. The check after the session still decides: only that run counts, and the card says how often the session ran the tests itself. A session that reviews or writes text gets no such tool. A task whose check cannot run because another session uses the project's files waits and is checked when they are free; it is never handed to you as work to accept that nobody checked.

### A box for commands

- **`hoprig box run`** runs one command with no network, without your home, seeing only the folders you name: `hoprig box run --write . -- npm test`, with `--read` for a folder it may only read. It is for what a coding session wrote (its tests, a script it made): run as you, such a command could read your sign-in files and keys and send them out.
- **When there is no box, nothing runs.** Before the first command, and again after ten minutes, the box tests itself inside the real box on this computer (six trials: a file in a home, a listener on this computer, a write outside, a process outside, and more). Only that yes lets a command run. There is no fallback and no setting or variable that switches the box off.
- **What is inside is a list, never the disk minus a list:** the system's programs read-only, the Node.js that runs Hoprig read-only, a home and a temporary folder of its own in memory, and the folders you named. A write folder's `.git` is read-only inside, so nothing a command writes there runs later outside. A named folder is one place however its path is written, and one reached through a link of your own is refused. The command gets a short environment of its own, never yours; at the timeout every process of the box is ended; its output is kept up to a limit.
- **`hoprig box check`** says whether this computer has a box, and when not, why and what would give it one (exit 0 or 3; `--json`). `hoprig doctor` shows one information line about it, never a warning: a computer without a box is not broken.
- **Per system.** Linux: bubblewrap, found only at its fixed system path. macOS: a `sandbox-exec` profile is written, and has not yet been run on a Mac. Windows: no box, said in one line.
- **What it costs,** measured on one computer: a small command takes about 11 ms longer in the box (`/bin/true` 3.2 ms against 14.5 ms; `node -e 0` 35.5 ms against 43.7 ms); one `hoprig box run` from the command line is a fresh program with its self-test, about a quarter of a second.
- **What it does not promise** is said in `docs/BOX.md`: it is not a virtual machine, and code inside can use the processor and read the listed system folders.
- Nothing of it runs by itself while missions are off. With missions on, a task's tests run in it when the task's session ends (Work: missions, above).

### Work: for another program

- **A token for a script or another product** (Settings → Work). You make it on the page, give it a name, and see it once; Hoprig keeps only its hash, lists it with when it was made and last used, and revokes it with one press (`hoprig tasks tokens` lists and revokes in a terminal). With it a program can add a task and read the tasks it added with their results (`Authorization: Bearer hwt_…` on `/api/work/token/tasks`), and nothing else: every other route of the dashboard refuses it. Limits per token: requests a minute and tasks a day.
- **A task from a token is someone else's words.** It says "From <the token's name>" wherever it is shown (the list, Today, its runs in Activity, the Operator, Tia's card), it never starts by itself, and when a session does it, its text goes into the brief as data from outside.
- **Webhooks**: an address, the events (item done, result ready, needs you) and a secret shown once. A delivery is a small JSON body signed with HMAC-SHA256 over its time and body; the answer's text is in it only when you turned "send the answer too" on. It goes to https only, follows no redirect, connects to the address that was checked (a private or local address only for a webhook you marked "on my own network"), waits ten seconds at most and tries three times; what it gave up on is said in Activity with the status only.
- `docs/WORK.md` has a ten-line script that adds a task and a twenty-line receiver that checks the signature.
- With no token and no webhook (as after the update) nothing of this runs, writes or connects.

### A new project from a brief

- **`hoprig project new <name> --brief <file>`** keeps your brief, unchanged, as the project's `docs/brief.md` and puts the bundled **new-project** skill into the project, so that every coding tool that opens it finds it. `--kind` is your hint of what it is (a website, a web app with accounts, a multi-tenant product, an internal tool, an API, a mobile-first product, a command-line tool, a library, a browser extension, a desktop app), `--scope product` or `--scope setup` says whether the AI builds the whole product or only its foundation, and `--start` opens a session in the App that begins with the skill. The Projects page has the same: the brief, the kind, the scope and **Start with AI**.
- **The skill fits the work to the project.** It works out what kind of project it is, how big its data and its traffic can get, and which of its parts apply in full, in a light form or not at all. It shows you that in ONE message, with a recommended answer to every open question, and waits for your one reply. Then it writes the project's documents (the brief, the flows, a test matrix, a checklist with a row for every rule, the decisions) before any code, builds in a fixed order, and ends with a review and a report with proof. A rule that protects people or data is never made lighter by the kind or the size of a project.
- **Your own defaults** (the language you are answered in, your country, your providers, your hosting) are read from `ai_brain/project-defaults.md` in your workspace when that file is there. Hoprig never writes it.

### Skills learned from your own work

- **Learn skills, off until you turn it on.** In Settings → Learn skills you choose a provider and a model. From then on, when you send a Work run back with words, or press **Learn from this** on a run, a look reads that run and drafts a skill: what should be done next time. The draft is scanned, tried on two or three requests with and without it, and waits under Skills → Learned with what it changed in those tries. Nothing is installed without your **Install** (one commit in the AI brain; nothing is pushed), and **Undo** takes it out again. By default at most five looks and three drafts a week; each look's cost is noted.
- **What a draft may not hold.** A draft that names a person, a computer, a path or a key of yours, that tells the agent to stop asking, to push, to delete or to fetch its instructions from the internet, or that has a line too long to check (over 2,000 characters), is refused with the reason, at the draft and again at Install.
- **Masking secrets and scanning a skill stay fast on a very long line.** Some of their patterns took time with the square of a line's length; a line of a few thousand characters could hold the dashboard for seconds.

### Proposals for a skill's text

- **A better text for a skill arrives as a proposal, and waits for your tap.** Where a search over the assistant's own eval found a text for one of her skills that does better, the proposal shows on the Skills page: what would change, the cases it was measured on, both texts' fresh samples and their spread. **Accept** puts it in place, with **Undo**; **Not now** leaves everything as it is. A proposal for a tool's description is never accepted by a tap: it can only be copied, as a text for a person to look at. A proposed text that names one of her tools is refused, also when the name is written with look-alike letters or split by signs. Nothing is searched, asked or changed by the dashboard itself: a proposal is a file that was delivered to it.

### Setting up a computer: optional kits

- **PHP + database** and **Flutter versions (fvm)** are two new optional kits beside Docker: off by default, never taken by `--yes`, installed only when you choose them (`hoprig pc setup --kits php,fvm`, or a tick on the Setup tab, where **Install…** opens the sheet first and shows the exact commands). The PHP kit is your package manager's own PHP command line, Composer and MariaDB; where a MySQL client is already there and the package manager would replace it, MariaDB is held back and said. fvm is `dart pub global activate fvm`, for you only.
- **Suggested, never ticked.** `pc setup`, `pc status` and the Setup tab name a kit that a project already on this computer points to (a `composer.json` or `artisan`; a `.fvmrc`), with the reason. The tick stays yours.
- **The PHP a project asks for.** For each PHP project, `require.php` of its `composer.json` is read with Composer's rules and held against the PHP here; when they do not fit, one note says so and what you can do: another PHP on your PATH, another series of the same package manager, or the project in Docker with the official image. Hoprig never removes or downgrades a PHP, adds no package source and never changes which PHP `php` runs.
- **Java is found, never installed.** Hoprig looks in `JAVA_HOME`, your PATH and Android Studio's own Java, and shows the first that runs ("Java 21.0.6, found in Android Studio"). When `JAVA_HOME` names another one or nothing that runs, the line to add is shown with the file it goes in; nothing is written for you.
- Nothing of this runs by itself: the projects are read when you open the Setup tab or type `pc status`, `pc setup` or `doctor`.

### Setting up a server

- **A server with only a root login.** Run as root, the installer makes the user `hoprig` (no password, bash as its shell, root's SSH keys copied so you log in the same way, a sudoers file of its own unless you add `--no-admin`, lingering on), installs Hoprig for it and starts its dashboard; nothing of Hoprig is left under `/root`. `--user NAME` picks another name. The steps are listed before the yes, each with its exact command.
- **`hoprig move-to-user` moves an installation that already runs under root.** It shows what runs and what would be copied (`--dry-run` only shows it), asks once, checks first that the user's own install can reach the network, makes the user where there is none, copies the settings, the state, the workspace and the coding tool's conversations (each under its new folder's name), checks the copy, and switches: root's dashboard stops for about half a minute and the user's answers on the same port with the same password. Root's copy is kept, and `/root/HOPRIG-MOVED.txt` says so. A stop on the way starts root's dashboard again and says what failed and how to go on. `--back` is the step back, and when the move runs again a copy the user's dashboard has used is set aside beside it, never deleted.
- **The same from the page.** Settings → **Runs as root** says where Hoprig stands and has **Move Hoprig to an ordinary user** (the look first, then one confirmation that names the server) and **Keep Hoprig on root on purpose**; a main computer can move a server it manages from that computer's page. `hoprig doctor` and Health say that Hoprig runs as root and what follows from it, as information only once you chose to keep it.
- **Set-up never opens a server to the network.** A computer counts as a server when it is reached over ssh and has no desktop of its own, when its hardware names a cloud, or when its network card has a public address. There the default is "only this computer"; `--access network` is refused, with the reason and the ways to reach the dashboard; a run of set-up closes a dashboard that was left open, after a yes; and `hoprig doctor` fails an open one, naming `hoprig setup --access local`.
- **How to reach it, in place of a link nobody can open.** On a server set-up prints no QR code and no link to a private address. It says how to open the dashboard: **Computers → Add a computer by SSH** on your main dashboard, the public link, or one ssh forward line. Settings → Security → Network says the same.
- **The dashboard keeps running after you log out.** Lingering is one of the listed steps that need administrator rights, shown and run under the same yes as the others, no longer a line to run yourself.
- **One closing list: "Still yours to do".** What the computer still needs from you (git's name and e-mail, the GitHub sign-in, the coding tool's sign-in) is said once, at the end, each with its one next step.
- **Add-ons install with the npm of the Node that Hoprig runs on**, so "spawn npm ENOENT" no longer comes in a shell or a service that lacks nvm's path, and with the install scripts the gateway's own README names.
- **A dashboard that cannot say where it listens is never called running on a server.** Set-up says that it cannot read where the dashboard listens, names the restart, and ends "not ready"; before, such a run ended "ready".
- **`hoprig doctor` on a server fails a gateway that Hoprig started and that listens beyond this computer**, and names the restart, or the words to add to the gateway's definition first. It reads the system's own table of listening ports; it connects to nothing.
- **At the desktop, a server reason that an earlier run over ssh saved is named**, with the way out (`hoprig setup --access network`); `hoprig doctor` says the same. And a dashboard that is closed to the network but kept for your Tailscale devices is said to be that, in set-up and at the end of the run.
- **The Install sheet of an add-on shows on the page.** It never did: the page's list did not say which parts of an add-on build a helper program. Now it names them and the exact command before anything is installed.
- **Smaller things.** `hoprig doctor` over ssh no longer finds Node at the top and calls it missing below. "…is not ours: left as it is" is no longer said about the command npm itself just put there. A language your terminal sends and the server lacks no longer prints warnings into set-up's output, and the service is not started with it. The installer reads past an os-release file that does not parse.

### A server from the dashboard

- **Add a server with its key file.** **Computers → Add a computer →** "I can reach it by SSH from this computer" **→** "I have a key file for it": its address, the user, the SSH port, and the private key pasted or picked. The page first shows the server's host key print, and nothing logs in until you press **It matches**. The key is kept only in Hoprig's own folder for keys (mode 600), never in the settings file, a log, an error or Activity, and the page never shows it again; a key with a passphrase is refused. When the server later shows another host key, everything to it stops until you choose **Use the new host key**. Adding the same server a second time under another address is recognised by its host key print.
- **Install Hoprig there from the page.** When Hoprig is not on the server yet, **Install Hoprig on** *its address* runs the installer there with the same key and shows its lines as they come.
- **Each computer's Health.** A computer's page has a **Health** part: its checks (those of `hoprig doctor` there) with a **Fix** on each line Hoprig can fix, Hoprig's and the coding tools' versions, whether its dashboard runs as a service, where it listens, its load, memory and disks. It is read when you open it or press **Refresh**, never on a timer; a computer that does not answer says since when, and nothing of it is shown as fine.
- **A gateway on a computer, from the page.** Under **Gateways** in the same part, each gateway of that computer can be installed, started, stopped and **run as a service** (a systemd user service on Linux, a launchd agent on macOS; the file in full and the commands are shown before anything is written, and **Remove the service** takes them away). Each press acts on what really runs and says what it did: **Stop** stops its service and also a copy started outside it, **Start** leaves such a copy running and says so, a stop that is refused is said and never called "restarted", and a start through a service answers once the gateway answers, or says that it does not yet. Where that computer's services start only after you log in there, the page says so and offers **Let them start after a restart** (an administrator step; where `sudo` asks for a password, the page gives you the command to type there once and never takes the password).
- **One rule for where a gateway listens.** Every start (Health, Settings → Add-ons, Tia, a session, the start again after an update) and its service follow it: on a server, and where that computer's dashboard listens on that computer only, the gateway gets `HOST=127.0.0.1` and its definition's own words for it; where you opened the dashboard to your network, it listens as it always did.
- **A first password is shown once.** A gateway of your own can name a word of the line where it prints its first password (**Add a gateway → More →** *Its first password's line*, or `hoprig gateways add … --first-password <word>`). Then a start shows what it printed first on the page, once, and that line is kept out of Hoprig's log. A gateway that names none is logged as it prints, readable by that user only, and the Start confirmation says so.
- **Open its page.** A gateway's own page is never shown under the dashboard's address. On this computer it is a plain link under the other loopback name, never a name you are signed in under (a browser sends a name's sign-in to every port of it). For a gateway on a computer added by SSH, the dashboard opens a forward on its own computer and gives you the link and **Stop**; it closes after 15 minutes with nothing moving. For a computer linked without SSH the page says in one sentence where to open it.
- **Install, update and a Fix are your own press.** Each asks first, naming the computer and what it runs, wherever it is pressed (Health, Settings → Add-ons, Providers), and the computer itself checks that name. Tia proposes each as a card you confirm, for exactly that gateway or check on that computer; starting and stopping a gateway stay hers at her level.
- **What still needs a terminal on the server:** Claude Code's install and its sign-in, adding its providers (a subscription's sign-in or an API key), and a `sudo` password wherever one is asked. A suggested skill is added on that computer's **Skills** page, and a restart is on its page under **Advanced → Power → Restart** where the system lets your user restart it without a password.

### Field reports

- **Hoprig learns from its own work.** Each report is made by code from a fixed shape (a kind, an outcome, a class, step names from a closed list), so nothing private can get into it; `hoprig field` lists this computer's reports and `hoprig field show <id>` shows one whole. When the same thing went wrong twice, Home says so in one line, with the help for that class, **Dismiss**, and **Make a skill draft of this**.
- **A way round stays on the computer.** `hoprig field way-round --failed "…" --worked "…"` turns what a session got round into a draft for the skill `ways-round`, which waits for your Install (with Undo). A command that works within an hour after the same kind of work failed names that command in one line.
- **Sending is your choice.** Settings → Field reports: never (the default), ask each time, or always, and only to the address you set there. What is sent is the file you were shown, byte for byte. `hoprig field inbox <folder>` reads a folder of received reports and groups them by version, system, kind and class. More in `docs/FIELD-REPORTS.md`.

### The editor

- **Keys you know.** Every command has the key of the editor people know; where a browser tab keeps a key for itself (Ctrl+N, Ctrl+W, Ctrl+T), the command gets the nearest one the browser leaves alone, and the command palette says so in one line. Ctrl+B hides the side bar, Ctrl+\` and Ctrl+J open a terminal panel in the folder.
- **Tabs**: a menu on each tab (Close, Close Others, Close to the Right, Copy Path), reopen a closed tab, drag to reorder.
- **Replace across files**, with a preview by file and one press to apply. A file that changed on disk since the search is skipped and named, never written over; the count is the count of what is written; in an open file one Undo takes it back.
- **Match Whole Word takes a word of any script**, the same word in the page, in ripgrep and in git: a Persian word joined by a zero-width joiner, a Hindi word with its vowel signs, `m²`.
- **A search can no longer hold the dashboard.** A regular expression typed into the search box is never run on the server's own thread: a pattern that takes too long on a long line is stopped at its time limit and says so, while every terminal and page goes on.
- **The Explorer**: drag to move, cut and paste, Copy Path. **The status bar**: the selection's size, the encoding, the tab size.

### Desktop mode

- **Windows behave as on a desktop**, held row by row against Windows 11, macOS and GNOME. A window can always be reached: after the browser gets smaller and larger again each window is where you left it, drawn to fit meanwhile. Escape during a drag puts the window back. Snapping to halves and quarters is in the title bar's menu and on the keys.
- **Keys of its own**: one set of modifiers with the arrows, W and M, **Alt+Shift** by default (on a Mac Option+Shift), **Ctrl+Alt** or **Off** in Settings → Appearance; Alt+Shift+\` goes through the windows as Alt+Tab does on your computer. A key the editor or a terminal needs is not taken while the keyboard is in that window; F6 takes the keyboard out of a terminal or the editor in a window.
- **The bar says what needs you**: a mark and "needs you" on a session's button, "session ended" for one that ended while it was minimised.
- **Touch**: grips and title-bar buttons are large enough for a finger on a tablet.
- **Two tabs on one desktop** keep one layout without a window ever jumping under the person who uses it: what you moved in your tab stays, the window you type in stays in front, and a tab you only look at does not change until you use it.

### The Hoprig skill

- **The skill without Hoprig: `npx hoprig-skill --claude`** (or `--agents`, or `--project <dir>`) puts the Hoprig skill into a coding tool's skills folder; `--dry-run` shows it first, `--remove` takes it away. It keeps a record of what it wrote, never replaces or removes a copy you edited without `--force`, and leaves a copy that Hoprig manages to `hoprig skills update`. Details: [the skill](/skill/).
- **The skill is made from the commands themselves** at every version: every command's own help is in its reference, and the build fails when a command it names changes. Its rules say which commands only look, which deletes need the user's word, and which steps (a sign-in link, a pairing code, opening the dashboard) are the user's own.
- **`hoprig skills update`** shows a changed file before a new one, so an edit of yours that the update would take away is in view.

### Fixes

- **One conversation, one card.** A conversation that runs in a terminal and is also open in the App (to read along) was listed twice on Home, once as the terminal that works and once as an App session that waits. Now the dashboard's pages (Home, the list of sessions, the counts in the sidebar) show it once: the terminal that runs it. The App session stays open in the App, to read along, and its own card is back on Home when that terminal has ended.
- **`hoprig demo` shows made-up data only.** Its Health page, the Operator's figures for the computer and its gateway (a pretend one on a port of its own) are sample data; the demo asks nothing of this computer's real services or its real gateway.
- **Every model picker shows the provider's own models.** After a provider was chosen, the Tia page, "Plan with AI", "Do it", the new-session sheet, the App's model menu and Settings offered only three family names. Now each lists what that provider serves: a gateway's or an API endpoint's own list (asked with that profile's own key, kept ten minutes, joined with the models the profile itself names), a Claude subscription's models, another coding tool's own list. Where no list can be had, the three family names stay, with one line saying why and a field for an exact name, which the server checks. A saved model that the list leaves out is kept and marked "not in this provider's list". No key and no provider address reaches the page; an address that holds a name and password is named as such, never shown. Nothing is asked by itself: a list is asked when a picker opens or a chat's page is open.
- **"Open in terminal" twice opens one terminal.** A second request for the same conversation (a double tap, two tabs) waits for the first and opens that terminal; before, it could answer with an error in the moment before the new terminal was known.
- **"Bring up to date" says why it could not.** When git refused a fast-forward for a reason Hoprig did not know, the Operator page, the project's page, `hoprig sync` and Tia all got a bare "fast-forward failed". Now git's own reason is said. One case is recognised and named: a tracked file that is changed here and by the incoming commits but that `git status` does not show (a file marked "assume unchanged" or "skip worktree"): the file, that nothing was changed, and the two commands that take the mark off. A file inside a private folder (`no-ai/`, `ignore/`) is never named, to you or to an assistant: the folder and a count are said, and the command that shows you the names in your own terminal.
- **Windows: a program is found by the file Windows can start.** npm puts three files side by side for a tool (`tool`, a shell script Windows cannot start, `tool.cmd` and `tool.ps1`); Hoprig took the first, so the shipped gateway never started on Windows. It now takes the one with an extension Windows starts.
- **A help word after a command only prints help.** `help`, `--help` or `-h` after any command, or after any of its subcommands, prints that command's help (a subcommand's own lines where it has them) and does nothing else: no file is written, no program started, no connection made. Before, some commands took the word as a value and acted: `hoprig pair help` made a real pairing code, `hoprig link help` a sign-in link, `hoprig machines join help` connected by SSH to a computer named "help", `hoprig service uninstall help` turned the background dashboard off, `hoprig auto on --help` turned Auto mode on, and `hoprig get <name> help` asked GitHub who is signed in. The plain word `help` stays a value in five places only: a task's title or note (`hoprig tasks add`, `tasks edit`), the words of a skill search (`hoprig skills find`, `skills search`) and the text of `hoprig field way-round`; `--help` and `-h` are help there too. After `opencode`, `codex`, `run`, `auto` (other than its settings) and a profile's name, the words go to the coding tool. `pair` and `link` refuse a stray word, and so do `claude status` and `claude update`.
- **A shell command of an OpenCode chat that the delete scan cannot judge is a card.** Before, an error inside the scan could leave the question with no answer and no card, and the session waited.
- **Remove on the main dashboard no longer says it could not revoke a token that it did revoke.** Removing a computer that is linked directly sometimes ended with the note "To be sure, also remove … there", although that computer had given up its token: the computer closed the link while its answer was still on the way. It now lets the answer arrive, then closes the link within a few seconds.
- **A new project needs no global git identity.** `--git-name` and `--git-email`, the setting `gitIdentity`, a question in the terminal, or two fields on the page give the first commit its name; your global git settings are not changed.
- **A project's example `.env` is not copied when the project has another `.env` file already**; the dry run and the run say the same.
- **A file that differs only by its line endings is said as that**, not as a change of yours.
- **A dashboard with many open sessions answers while it starts.** Starting a program holds the server's one thread for a moment, and a start, the upkeep's round or the first open of Home started twenty and more at once: with fifty open sessions nothing was answered for up to 150 ms at a time. Program starts now take turns and each step of the round gets a pass of its own; the longest such stretch measured on the same home is under 30 ms.
- **Allow and Do not allow keep the keyboard's focus.** The card of a session that asks for your OK is drawn again every few seconds, and the focus was lost each time: Tab to Allow, a short pause, Enter, and nothing happened. The focus now stays on the same answer through a redraw, on the session's page, on Home and on Workspace.
- **A project with a file name that is not UTF-8 is copied on every Node.js.** `hoprig adopt apply` copied a folder with Node.js's own copy, which on Node.js 22.11 failed on such a name, and stopped on a socket or a pipe in the folder. Hoprig now copies by the names' bytes itself (files with their mode and time, links as links, a socket or a pipe left out), the same on every supported Node.js. And the check after the copy no longer refuses a correct copy when a file's time lies within two thousandths of a second of a full second.
- **`hoprig doctor --offline` on Linux starts no package manager.** It counted waiting updates with the system's own tools also when told to stay offline; now it says "updates not checked", as on macOS, and still says when a restart is pending.
- **`hoprig doctor` checks the port the dashboard really uses.** A dashboard that runs says where it listens, and that port is checked; when none runs, it is the port a start would take (the environment's `PORT`, then the settings, then the default). A `PORT` that is not a port number is said, not probed. The line about access names the same port.
- **A session's terminal draws a coding tool's rounded frames and marks whole on Linux** (⎿, ⇧, ⏺), in a font of the terminal's own width, on computers that have Chinese or Japanese fonts; before, a frame's corners stood off its side bars. The ⇧Tab key draws its arrow like the other keys there too.
- **The demo's Overview no longer calls Claude Code "The newest version"** while Settings → Updates offers a newer one: every made-up version of the demo comes from one place.
- **The demo's Providers page says who is signed in to Claude Code**, so "Claude Pro" and the question "who is signed in" agree, and no program is started to ask.
- **Plainer words in several refusals.** A provider a coding tool cannot use: "it does not work with that coding tool". A changed check limit names Settings → Go live. The public link without a password names Settings → Security and sign-in and says why it needs one. A gateway program changed after you confirmed it says what to do whether you changed it or not.

### Windows (used by hand once, not supported yet)

- **Installing the service again, or an update, no longer leaves the old dashboard serving.** The old `serve` is ended by its own process id, and only after it is shown to be that very program: started when its record says, with Hoprig's own command line, as your user, and answering with its record's key. Anything else is named and never ended. The gateway and the public link keep running.
- **The background task is made for your account by its SID**, so a Microsoft or a work account and a name with other letters work, and it keeps running on battery.
- **Programs that winget installed are found without a new sign-in:** Path is read again from the registry. The stand-in `python` of Windows is no longer taken for Python, and the Python kit names its last step.
- The shipped gateway starts without a shell. Long paths are named as information, with what turning them on helps.
- None of these was tried on a Windows computer yet; the README says what was.

### For contributors

- **The test suite cannot touch the computer it runs on.** `npm test` puts stand-ins first on the PATH of every test: for sudo, systemctl, loginctl, the package managers, a global npm, ssh, the GitHub CLI, docker, tailscale, cloudflared and more programs that reach beyond a test's own home. A test that reaches one fails the run by name ("A TEST REACHED THE REAL …"); a test that needs such a program puts its own stand-in first (`test/seal.mjs`). This holds however a child is started: with no PATH, with a cleared environment, from a Node child or a worker thread, and by a full path, where only git, Node, a shell, `env` and `bwrap` may be started, and a program a test names with its reason (a browser, `ssh-keygen`).
- **A test sees only what is its own.** `ps`, `ss` and a listing of `/proc` show a test its own processes and listeners and nobody else's, and `df` answers one made-up disk. A connection to a port the product uses by default (the dashboard's, a shipped gateway's, Caddy's admin port) is refused before anything is sent, so a test never reaches a dashboard or a gateway that runs on your own computer. `AGENTS.md` and `CONTRIBUTING.md` say what each line of the runner means, what to do about it, and what the seal does not hold (a program started from a shell string, among others).
- The test runner fails a run that left a new entry in the repository's root, by name, and (on Windows always, elsewhere with `HOPRIG_TEST_HOME_GUARD=1`) one that changed the real home's Hoprig or coding-tool folders.
- **Tia's eval runs a case that failed once more at the end of the run.** A case that passes then is shown and counted apart from a clean pass; only a case that fails twice counts as a regression or sets the exit code, and a recorded baseline lists such cases apart.
- A test whose process outlives it now fails and names the process (on Linux), instead of a folder removal that retried until it happened to succeed.

### Releases

- **A release is a tag on a commit of main**: the tests, the GitHub release with this changelog's section as its notes, and both packages on npm with provenance, through npm's trusted publishing, only while the release workflow's publishing switch is on.

A Work page where a coding session can do a task for you, an App that works more like the Claude Code desktop app, groups of projects of your own in the workspace, and gateways of your own. Everything new in this version was run on Linux only.

### What changes when you update

- **Hoprig is now under the Apache License 2.0.** Versions up to and including 0.2.1 keep the licence they were released under ([License](https://github.com/allswebtech/hoprig#license) in the README). A NOTICE file names the copyright holder, a pull request is merged once its author agrees to the [contributor licence agreement](https://github.com/allswebtech/hoprig/blob/main/CLA.md) by one line in it, and the name and the logo have a [trademark policy](https://github.com/allswebtech/hoprig/blob/main/TRADEMARKS.md).
- **A folder of your workspace that is a link you made yourself is no longer followed until you name it.** A project folder, a code folder, the AI brain or a folder of the tree that leads elsewhere (to another disk, for example) is not synced, restored or set up, and the map is not written through it. `hoprig workspace status` lists each such link with the command that names it: `hoprig workspace mylink add <path>`. This keeps a link that came with a cloned repository from making Hoprig act outside that repository's folder.
- **New session asks first: App or Terminal.** The App is what was called a chat. In the page a chat is now a session in the App, for example in a schedule's **Open as** (App or Terminal).
- **The permission modes have Claude Code's own names**: Manual (was Ask first), Accept edits, Plan, Auto and Bypass permissions; Don't ask (was Never ask) is under **More modes**. In a session, Close is now **Archive**, **Open in terminal** is **Open in → Terminal** in the session menu (and a button in the title bar), and **Files** and **Changes** moved from the folder chip to the title bar.
- **A session's cost shows only in the Verbose transcript view**, and only for a provider billed by use. The status line no longer shows it.
- **The workspace map's version 2, which groups need, is written only when you run `hoprig workspace map --upgrade`.** A computer with an older Hoprig refuses a map of version 2 and its map then stands still, so update Hoprig on every computer first. Without groups nothing changes.
- **A project belongs in a folder of its own name.** `hoprig get example/shop-workspace` makes `shop/`. When a project of your map is here under another folder name, restore and `hoprig workspace status` show the `mv` that gives it the map's name and count it as needing you; nothing is moved by itself.

### Work

- **Your tasks and a Today screen, in one file of your workspace.** **Work** is under Home in the menu. **Today** shows what needs you now (tasks due this week or waiting for you, and the sessions on any of your computers that need an OK or reached a limit), what a session finished (**To review**), this week day by day and what was done lately. **Tasks** lists every task, with filters by project and by who does it. The list is one file in a git repository, the AI brain by default; **Settings → Work** chooses another place.
- **Do it: a coding session does a task.** The ▷ button on a task shows the brief, the project and folder, the provider, model and effort, then starts a session in the App with that brief. When its turn ends, the task waits in To review with the session's answer, its commits and the files it left changed: **Accept** marks it done, **Send back** opens it again with what you wrote added to its brief. Nothing is pushed or merged by it.
- **Activity lists every run**, newest first, by day. A run is a small file beside the list, with keys, this computer's paths and its name taken out, so the other computers see it after a Save. A brief that holds characters that cannot be seen is refused, with **Take them out**.
- **Save commits only Work's files, and either reaches the server or leaves your change in the file.** It brings another computer's changes in task by task and asks you only where both computers changed the same task. It never sends a commit of yours that changes anything else, and a save that was interrupted is finished the next time.
- **`hoprig tasks` does the same in a terminal**: `today`, `list`, `add`, `edit`, `done`, `do`, `runs`, `save` and more, each with `--json`, and `--dry-run` where it changes something. The command is `tasks`, so a provider named `work` keeps working. Details: [Work](/docs/work/).

### The App and New session

- **New session is one popup**: App or Terminal, the coding tool, then the project. A coding tool that is not ready says what it is missing. A tap on a project always starts a new session; where one runs already, **Open running session** is its own button beside the row.
- **A title bar as in the Claude Code desktop app.** The caret beside the title opens the session menu: **Transcript view** (Normal, Thinking or Verbose, kept in this browser), **Open in** (Terminal, Files, Changes), **Archive**, **Copy branch name** and **Rename**. The title bar has **Open in Terminal**, **Changes** and **Files**, and its ⋮ menu has **Background tasks** once there are some.
- **A session rail beside the chat on a wide screen**: where the session runs, its provider and branch, the folder's changes (their +N −M opens the editor's Changes), the context and the background tasks with **Stop**. **Hide session rail** is in the title bar.
- **A plan's answers in Claude Code's words**: "Yes, and use auto mode" (offered only once the session has shown it can), "Yes, manually approve edits" and "No, keep planning". Before, the first answer never went on in auto mode.
- **An answered OK folds into the tool card it was about** ("Ran npm test · allowed by you"), a queued message shows as you sent it, with its files by name, and a change of a file that failed reads "Could not write …".
- **Fixed**: a turn that starts from your queued message is no longer labelled as one the coding tool began by itself; a session's title survives **Open in Terminal** and the way back, also across a restart of the dashboard; a request an older Claude Code does not know is refused in plain words; an OpenCode session's Thinking view no longer says Claude; a plan no longer offers auto mode after a move to a provider or a model without it. The title bar's and the rail's controls are big enough for a finger, and after a choice in a menu the keyboard is back on what opened it.

### The workspace

- **`hoprig get <name>` fetches a project by one word**: the parent, every code repository, the memory link, the git hooks, a `.env` from `.env.example` and the installs (asked). A bare name is looked up in your map, then on GitHub as `<name>-workspace` and `<name>`, and the folder is the project's name whatever its repository is called. A project that is here already is not changed: `get` says what it misses, and `hoprig project setup <name>` sets it up.
- **A dry run changes nothing at all.** `hoprig get`, the `hoprig project` commands and the workspace commands take `--dry-run` and then only say what they would do: no lock, no settings file, no map, no git ref is written.
- **Groups: folders of projects of your own**, beside the projects folder and written into the map, so every computer gets them: `hoprig workspace group add client-work`. A group can also be a repository of its own that holds projects. A place can carry a naming rule: `hoprig workspace find --in <place>` lists what your GitHub account has that fits it, and `hoprig get <word> --in <place>` fetches it. A project in a group is named `<place>/<name>`, and the Workspace page shows one section per place. Details: [Workspace](/docs/workspace/).
- **A group may bring a command of its own.** It is made only after your yes on that computer (`hoprig workspace tool allow <group>`), and checked again at every start.
- **`hoprig workspace rules`** shows a short text about your workspace for coding sessions, and `--write` puts it, after your yes, into a file of Hoprig's own (`~/.claude/rules/hoprig-workspace.md`). Nothing from the map goes into a file a coding tool reads as instructions without your yes, and your own working rules are never touched.
- **`hoprig project new --github` names the repository `<name>-workspace` when your account has `<name>` already**; `--repo-name` chooses another name. A key of `project.json` that this version does not know is kept and shown as a warning, instead of stopping a clone.
- **One address in every spelling**: ssh or https, with or without `.git`, and on the usual hosting sites the owner and the repository in any letter case.

### Providers and gateways

- **A gateway of your own.** A gateway is a program that offers other AI providers through Claude's API. Beside the one Hoprig ships, `hoprig gateways add` (or **Settings → Add-ons → Add a gateway**) defines another: its program or npm package, its port and its own page. It is a program Hoprig will run, so you see the exact program and arguments and confirm with the dashboard's password; the assistant cannot add one. Hoprig runs exactly the file you confirmed, and asks again once it changes (`hoprig gateways confirm <name>`).
- **Other providers asks which gateway first** when there is more than one, and a provider whose gateway was removed says so.

### Safety

- **In a terminal session, the page answers only a permission, and only into the dialog its card shows.** **Allow** and **Do not allow** appear while Claude Code's permission dialog for that same command or file is on the screen. A question, a plan, or a screen that cannot be read sends you to the terminal, and with two questions waiting the page answers neither.
- **Bypass permissions follows one rule, in a terminal and in the App.** Claude Code still stops before some deletes in this mode. Hoprig answers by itself only a plain delete inside the folder the command runs in, the same in the App as in a terminal, and shows each one it allowed ("Allowed by Hoprig in bypass mode"). Every other stop of Claude Code's, a question, a plan and what your settings say "ask" for still come to you.
- **Hoprig stays inside each project's own folder.** A link that came with a repository is never followed, a file is never written through a link, and the map, a group's ignore file and the rules folder are never read or written through one.
- **More kinds of keys are masked** where Hoprig shows or keeps text (the AI brain page, Tia, Work's runs): Hoprig's own tokens, GitHub's fine-grained tokens, Stripe, Google and npm keys, and the password in an address.

- **Before Hoprig allows a delete by itself, it looks at what the shell will hand to rm.** Nothing is allowed from inside a repository's history, from your home, your workspace or a folder that holds projects; nothing that is a repository or holds one, at any depth; nothing reached through a link, on another disk or past a mount. It judges a pattern such as `*` by what it could match under any of the shell's options, also names that begin with a dot. Where it cannot tell in a quarter of a second (a very large folder), it does not allow: Claude Code asks you.
- **A delete with a word that begins with `-` after its first target is never allowed by itself.** The rm of macOS takes such a word for a file's name where the rm of Linux takes it for an option, so Hoprig allows such a line on no system. A git folder counts as one in any letter case of its name.
- **An OpenCode chat in bypass mode asks Hoprig before every shell command.** OpenCode has no stop of its own there. An ordinary command runs at once; one that names a delete in plain sight (rm, shred, find -delete, git clean, rsync --delete, also inside `bash -c`, `ssh` or `sudo`) and is not plainly inside the folder is put to you as a card. It is no wall: a script, a program, a command written to get around it and OpenCode's own file tools can still delete. What your own OpenCode settings deny stays denied; when they cannot be read, every command is a card.
- **A command an OpenCode chat asked about while the dashboard was down is taken up when it is back**, also with no page open: it runs if it is ordinary and shows its card if it is not. It never runs unanswered.

### Fixes

- **Sync no longer deletes a code repository or a group's project** that lives in a folder its parent ignores, when the parent starts to track a file at that place: git refuses now, and sync names the folder in the way. Before it suggests a merge or a rebase, sync says what either would delete.
- **On a busy computer, a running gateway, dashboard or editor server is no longer taken for one that stopped.** Only a port that refuses counts as not running. Before, joining a hub could stop with "the dashboard is not running", and the editor could remove a running code server's folder.
- **A paste into a tmux terminal that tmux did not read no longer stops the whole dashboard.**
- **With "stop an unused gateway" on, the automations keep running.** The public link made every check fail, which stopped the queue, the schedules, restore and retry.
- **Setting up a computer from a recipe** retries a project that needs you with its own fix, and a step run with sudo keeps a quoted path as one argument.
- **A long reply can no longer freeze a session's page or hold up the dashboard.** Three places that read text (the files named at the end of a message, the preview on a card, a heading) took a time that doubled with every few characters of certain text. Each reads its text in one pass now.
- **Two changes to a session's state at the same moment no longer lose one.** When a lock file was left behind by a process that had ended, two hooks could both take it over. The take-over is one step now, and only one of them makes it.
- **Ending or cancelling a Claude Code sign-in from the page no longer fails now and then.** Claude Code, just told to end, could still write into the sign-in's helper folder while Hoprig removed it; the page then got an error and the sign-in's text stayed in memory. The removal is tried again and never fails the end.
- **On macOS, a terminal of the built-in kind starts also when the terminal module's helper lost its executable bit in the install.** Hoprig sets the bit before every start. Run on GitHub's macOS runners, not on a Mac in use.
- **`npm test` no longer loses results.** On a busy computer the runner could end a test file's process before its last results were read, and the run still said "fail 0". Each file writes its results before it ends, a run whose file did not report everything fails and names the file, and a clean run ends with "every result arrived".
- **Esc typed in the terminal** settles the session's card at once, and **Tab** stays inside a popup whose last part is a closed Options section.
