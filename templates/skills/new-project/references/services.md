# Environment, storage, mail, payments and jobs

- Applies when: by part, and the applies table names each part. Env: always (a kind with no server: its own
  configuration, rule 13). Storage: when the project keeps files (uploads, generated files, archives). Mail: when it
  sends any mail. Payments: when it takes, holds or pays out money. Jobs: when it has scheduled work, or slow work and
  a database to queue it in. `full` when all five parts apply and none in a light form, otherwise `light`. It is never
  `not needed`.
- Light form: only "Env" and "Jobs" have one, written inside those parts. Storage, Mail and Payments apply in full or
  not at all (Mail without a database sends at once, as Mail says).

The providers are the details' choices (the owner's defaults name his); every rule holds for any provider.

## Env: these names only, the same in every app

1. `APP_SECRET`: the one root secret, typed by the owner and never generated by a tool, because it seals data. Every
   other app secret is derived from it (HKDF, one label each).
2. The public site address, `https://<primary domain>` (`NEXT_PUBLIC_SITE_URL` in Next.js; the framework's own
   public prefix elsewhere).
3. `DATABASE_URL` (the migrations role) and `APP_DATABASE_URL` (the running app's role).
4. `CRON_SECRET`: the bearer token for scheduled calls. It seals nothing.
5. The bot check's two keys (for example Turnstile: `NEXT_PUBLIC_TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY`):
   both empty means off, both set means on (invisible), and the check fails closed. It guards the public forms that
   can be abused: sign-up, code and password-reset requests, contact forms.
6. A deployment target that fills some names itself or marks them required, generated or optional (the owner's
   defaults name his target and its way): use its own way and write which in the deployment docs.
7. Everything else is never env. Provider keys (storage, mail, codes, sign-in providers, payments, AI and the rest),
   analytics and tag ids, admin mail addresses and phones live in the app's admin: sealed with `APP_SECRET`,
   admin-only, masked, each field with its console link and menu path, its format and a made-up example, validation,
   a Test button and a "How to set up" text. Constants (pool sizes, workers, storage folders, build switches) live in
   code. Who is an admin is a role on the user row, granted with a small server-side command
   (`node scripts/admin.mjs grant|revoke|list`).
8. The build passes with an empty database and no secrets, and `.env.example` lists only these names, plus the
   light-form names below.
9. A name whose thing this project does not have is left out everywhere: no database, no database addresses; no
   scheduled call, no `CRON_SECRET`; no form that opens without login and can be abused (sign-up, code, password
   reset, contact), no bot-check keys (an internal tool's code login or password reset keeps them, empty means off);
   no page, link or callback that needs the public address (an API called only on an internal host), no public site
   address; nothing to seal or sign, no `APP_SECRET`.
10. Light form (no database, so nowhere to seal a setting: for example a static website with a contact form): the
    few provider keys and plain settings the project needs (for example the address that receives the contact form
    and the sender address) are env names, each named in the one message, in `.env.example` and in `ENVIRONMENT.md`.
    They stay on the server and are optional at start: empty means the feature shows "not set up", a set value is
    validated. When the project gets a database, they move into sealed settings.
11. A project with a database but no admin area (an API only) is not a light form: it seals every provider key with
    `APP_SECRET` all the same and sets it with a server-side command (`node scripts/settings.mjs set|list`). With
    payments, an admin confirms a refund with a server-side command (`node scripts/refund.mjs confirm`), written to
    the audit log.
12. With no admin area and no database, nothing is sealed: rule 10 holds.
13. A kind with no server (a command-line tool, a library, an extension, a desktop app): its configuration is the
    user's own (flags, a config file in the user's config folder, the environment), validated at start with a plain
    message for a bad value; a key it needs is the user's, read from there, never shipped in the package.

## Storage

14. The endpoint, region, access key id, secret access key, bucket and public base address are admin settings
    (above), never env (with no database, the Env light form).
15. All storage code in one module, reading those settings. Switching provider means changing those settings only.
16. Private by default, with signed links.
17. Browsers upload directly with a presigned address (size and type signed) into a temporary folder, so files never
    pass through the app server. The server then checks the real type and size before accepting the file. A
    lifecycle rule deletes files that were never accepted.

## Mail

18. The mail provider's library or SMTP, on the server only. Login codes and other time-critical mails go out at once
    with a quick retry. The rest go through a background job with retries. A project without a database has no queue:
    it sends every mail at once with a quick retry, and the user sees a plain error when it still fails.
19. Reusable templates in one folder (for example `src/emails/`), each with a plain-text version.
20. The deployment docs cover SPF, DKIM and DMARC.

## Payments

21. The server creates the order and calculates the amount. Never trust an amount from the client.
22. Check the webhook's signature on the raw request body, before parsing it. The provider's payment id is unique, so
    a repeated webhook changes nothing. A status changes only along allowed steps (a late "failed" never overwrites
    "paid"), so webhooks arriving out of order are safe.
23. A `payments` table with a status (created, paid, failed, refunded) and timestamps.
24. A reconciliation job checks pending payments with the provider, so a missed webhook never loses a payment.
25. Refunds happen only after an admin confirms them.
26. Tests: bad signature, repeated webhook, changed amount, late webhook, failed payment.

## Jobs

27. The simplest runner that fits the deployment. A server of its own: a separate worker process, with a PostgreSQL
    `SKIP LOCKED` queue while the volume is low and Valkey or Redis (for example BullMQ) once jobs are frequent, to
    keep load off the main database. Serverless: the host's cron plus a queue service. Write the choice in
    `decisions.md`.
28. Every job is safe to run twice, retries with backoff and never does anything irreversible without approval.
29. Repetitive work the product needs (reminders, clean-ups, reconciliation) is automated as a job.
30. Light form (only scheduled work, no queue): scheduled calls guarded by `CRON_SECRET`, and no worker process. The
    other rules of Jobs stay: safe to run twice, retries with backoff, nothing irreversible without approval.
